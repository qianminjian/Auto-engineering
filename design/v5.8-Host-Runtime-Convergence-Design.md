# v5.8 Host Runtime 产品闭环收敛设计

> 日期：2026-08-16｜状态：已批准实施｜阶段：Phase 83｜任务：T460-T469

> 2026-08-25 实施战略纠偏：本设计中的 Driver、Assembler、事件和 Gate 均为
> `P0-E2E` 的支撑能力，不再按组件通过判定产品完成。唯一产品出口及冻结边界以
> `design/v5.8-End-to-End-Product-Closure-Design.md` 为准。

## 1. 问题与目标

第 20 次真实运行证明，Loop 的协议组件已经存在，但产品执行链仍未闭合：Core 输出
`CONTINUE` Action 后，宿主可能结束回复；Worker 已完成后，Coordinator 仍需手工拼装
receipt、attestation 和 total proof；Plan refine 后进度可达到 140%；Research 建议可在
`semantic_enforcement=partial` 时进入实现义务；组件测试未覆盖真实 Skill/Command/Hook。

本阶段只以一个结果为成功：用户启动一次 Loop 后，除真实 `WAIT_USER`、资源等待、终态或
不可恢复错误外，安装后的宿主必须持续执行 Action 并最终到达 `TERMINAL`。组件测试、内部
轨迹和 archive smoke 只能证明支撑能力，不能关闭该产品目标。

## 2. 不可变边界

1. Core 保持单 Tick、确定性、无 LLM、无后台 daemon。
2. 宿主负责原生 Worker、工具执行和用户交互；Core 不伪造宿主事实。
3. 不增加用户可见的 `continue`、`supervisor` 或会话管理命令。
4. EventStore 是执行事实唯一来源；投影可删除后重建。
5. 显式设计文档是权威来源；Research/Critic 不能自行改变 binding decision。
6. 当前严格 Action 只消费 `spawn.invocations[]`；旧字段只由版本迁移器读取。

## 3. 目标架构

```text
User invocation
  -> HostRuntimeDriver
     -> Core Tick -> Action + ExecutionControl + HostExecutionTemplate
     -> native Worker / inline developer / user gate
     -> HostExecutionAssembler (atomic evidence transaction)
     -> Result preflight (all violations at once)
     -> Core Tick -> EventStore append
     -> Reducers -> projections -> next Action
     -> StopGuard (only TERMINAL / WAIT_USER / ERROR may yield)
```

### 3.1 HostRuntimeDriver

Driver 是插件层纯状态机，不调用 LLM，也不修改 Core 状态。输入为当前 Action 和宿主实际
能力，输出为唯一下一步：执行 Worker、inline 执行、提交自动 Gate、等待资源、询问用户、
终止或失败。每次执行建立 `HostRunLease`，绑定 thread、action message、host session 和
runtime build。Stop Hook 读取 lease 与 active Action：若处置是 `CONTINUE` 且没有合法
完成/中断事实，则返回 block；平台不支持 Stop block 时，能力协商不得宣称
`continuous_invocation=true`。

### 3.2 HostExecutionAssembler

Core 只生成不可变 challenge 和 pending 模板。宿主将原生 Worker outcome 交给 Assembler；
Assembler 校验 worker 集合、原生 handle、prompt hash、effort、隔离证据和能力摘要，然后
以同一事务生成：

- 每 Worker receipt；
- 每 Worker attestation；
- shared total proof；
- Coordinator StageResult 的 `spawned=true` 及引用。

失败时一次返回全部 violations。Worker 已成功但证据落盘中断时，从 outcome journal 幂等
恢复，不重新 spawn。Core 不得把“缺少 Coordinator artifact”诊断为“重新创建 Worker”。

Worker 产出采用“私有 artifact 先行、共享汇总后置”的两阶段协议：invocation 的
`outcome_path` 是唯一 Worker 写入地址，Host Collector 在 Finalizer 前完成全量采集和
Action/worker 身份校验；Coordinator 不再承担创造 native outcome 的职责。宿主上下文即使
在 Worker 已完成后丢失，也只能留下可分类的缺失证据，不能留下“进程成功但无结果”的半
成功状态。旧共享文件仍可被兼容读取，但不产生新版本的严格成功证明。

### 3.3 事件与进度

新写入的完成事实必须包含 `batch_id`、`task_ids` 和 `completed_task_count`。Reducer 依据
这些事实派生 BatchState 和 ProgressTree；TickOrchestrator 不直接增加计数。PlanPatch
激活时，以完整合并后的计划重新计算总任务数，并按已完成 ID 保留完成事实。活动批次按
`batch_id` 寻址，数组下标只作派生 cursor。以下状态全部 fail-closed：

- `done_tasks > total_tasks`；
- `completion_pct > 100`；
- active batch 不存在；
- 同一 task 重复完成；
- 投影与 EventStore 重放结果不同。

### 3.4 设计权威

`semantic_enforcement=partial` 的含义是“只能保守执行原设计”，不是“允许建议补全设计”。
Research、Critic 或 Gap 若要求改变架构、安全边界、对外契约或 binding decision，Core 必须
生成 `WAIT_USER: DESIGN_CHANGE_APPROVAL_REQUIRED`。批准事件必须绑定 decision、source
digest、proposed change 和 causation；`apply_to_remaining=recommendations` 只授权既有合法
选项，不能批准新的架构变更。

### 3.5 Gate 处置的单一判定源

Gate 的展示类型（`decision`、`agent_escalation`、`state_reconciliation`、
`stage_checkpoint`、`manual`、`user`）是用户交互语义，不是宿主执行阶段。Core 在
`action_envelope` 编译 `ExecutionControl` 时必须按 Gate 类型统一判定：所有要求真实用户
选择、授权或确认的 Gate 都输出 `WAIT_USER`，并带稳定 `reason_code`；只有由 Core/宿主
可自动完成的验证 Gate 才输出 `CONTINUE`。Supervisor 只能消费该机器处置，禁止按
`stage`、`question` 或 Gate 文本猜测。

未登记或结构非法的 Gate 必须输出 `ERROR`（`UNKNOWN_GATE_TYPE` 或
`GATE_PAYLOAD_INVALID`），不得默认放行；新增 Gate 类型必须先进入该统一策略和回归矩阵。

该规则覆盖设计变更批准、状态协调、Agent escalation 和阶段检查点，避免出现“Action
外观是 Gate、机器处置却是 `CONTINUE`”的跨阶段断链。`WAIT_USER` Gate 不得进入
`compile_action_execution_request`，也不得创建宿主执行租约；用户选择通过同一 Gate
message identity 写回 Result 后，Core 才能生成下一 Action。

### 3.6 指标与产品资产

plan refine、Critic major、Tick、Worker、停止/恢复和 usage completeness 全部从 EventStore
事实投影。未知 token 记为 `measurement_incomplete`，不得记零。Skill、Command、Hook 和
schema 纳入同一 release consistency gate；当前合同不得出现旧 spawn 执行指令。

## 4. 错误与恢复

| 故障 | 确定性响应 |
|---|---|
| Worker 尚未启动 | 保留 Action，按资源/能力错误处理 |
| Worker 运行失败 | 写失败 outcome，不生成 completed attestation |
| Worker 完成、证据未落盘 | 从 outcome journal 幂等 finalize，禁止重新 spawn |
| Result 多项不完整 | 单次返回全部 violations，不推进 Tick |
| Host 尝试在 CONTINUE 停止 | StopGuard block，并返回下一 Action 摘要 |
| 平台不能 block stop | 启动前能力失败，不宣称全自动 |
| Plan refine 改变总量 | 原子重算 totals 后再激活，违反不变量则拒绝 |
| 建议改变原设计 | WAIT_USER 设计变更 Gate |

## 5. 验收架构

### L1：单元合同

Driver 状态表、Assembler 原子性、Reducer 不变量、批准因果链和指标投影分别测试。

### L2：插件内产品轨迹

使用真实 Skill/Command/Hook 资产和生产 Tick/EventStore，执行：Architect → Developer →
Critic MAJOR → Plan refine → Developer。断言无手工 JSON 修复、无意外 yield、进度不超过
100%、重放等价、指标等于事件事实。

### L3：安装后宿主 Canary

同一 Build 分别安装到 Claude Code 与 Codex；真实原生 Worker 完成至少一次 refine 轨迹。
证据包含安装来源、Action/Result/Event 因果链、StopGuard、receipt/attestation 和 usage
completeness。任何手工续跑均失败。

### L4：完整业务黄金项目（外部验收）

从明确设计文档运行到 `TERMINAL`。零意外返回、零手工 proof 修复、零未经批准的架构变更、
零投影漂移；两宿主 Core 语义等价。L4 还必须单独记录真实 API、上传、浏览器和设备权限
等业务链路的已验证/未验证边界；Core 的 `TERMINAL` 不能替代这些证据。L3/L4 未完成前不得发布新 RC。

## 6. EARS 验收条件

1. While active Action disposition is CONTINUE, when the host attempts to stop, the plugin
   shall block the stop or fail capability negotiation before the run starts.
2. While native Workers completed, when evidence finalization runs, the assembler shall
   atomically produce exactly one bound receipt and attestation per invocation plus one total proof.
3. While an outcome journal exists, when finalization resumes after interruption, the assembler
   shall reuse the outcome and shall not request another Worker invocation.
4. While a PlanPatch adds batches, when the candidate activates, the reducers shall recompute
   totals from the merged plan and preserve completion by stable IDs.
5. While any projection has done greater than total, when an Action is compiled, the Core shall
   reject the state and shall not emit another executable Action.
6. While semantic enforcement is partial, when advisory output conflicts with the design source,
   the Core shall emit a design-change approval Gate and shall not activate the change.
7. While metrics are produced, when EventStore is replayed, the metrics projection shall equal
   Critic-major, refine, Tick and Worker facts or report measurement incomplete.
8. While a release candidate is evaluated, when L3 or L4 evidence is missing, the release gate
   shall remain blocked regardless of L1/L2 results.
9. While a deep-audit observation is advisory or outside the binding design scope, when the Core
   evaluates findings, the observation shall remain auditable but shall not trigger PLAN_REFINE.
10. While native Workers have completed and their outcomes are journaled, when the host advances
    to another Action, it shall reclaim every completed native handle before requesting new capacity.
11. While a host tool changes its shell working directory, when finalize, validate or tick runs,
    the Core shall resolve protocol state and relative artifacts from the immutable Action project root.
12. While a current Action carries a Runtime Revision, when a HostRunLease is persisted, the lease
    shall bind the same engine build identity and shall never report that build as unknown.
13. While project tools execute from an installed plugin, when the host launches uv/test/build,
    the working directory shall be the Action project root and `.venv` shall never become plugin runtime.
14. While a Worker payload approaches the receipt byte limit, when the Assembler finalizes evidence,
    it shall budget the complete envelope and switch to ArtifactRef before any journal/proof commit.
15. While an installed product is executing, when any host tool targets the plugin tree, immutable
    release bytes shall be read-only and only the dedicated `.ae-runtime` subtree may be mutable.
16. While a sealed Claude plugin is upgraded, when official uninstall needs deletion access, the
    installer shall unseal only the enumerated user install inside the owned cache boundary and reseal the replacement.
17. While Claude Stop hooks execute or Core emits a terminal Action, when runtime identity is resolved,
    hook and terminal lease shall use the same dedicated runtime and non-unknown Build Revision.
18. While one supported host CLI is launched from another host process, when the installed plugin invokes
    Core, the current plugin-root signal shall identify the effective platform and session identity shall
    be selected from that platform; inherited outer-host variables shall not contaminate the run lease.
19. While Gap Scan evaluates a design against an existing project, when bounded ProjectProfile facts
    already resolve paths, commands or project mechanics, the scanner shall not promote those mechanics
    into a user design Gate unless an unresolved choice blocks implementation or changes external behavior.
20. While Claude transcript usage is enabled, when an absolute project path is mapped to Claude's
    project transcript directory, the leading path separator shall be preserved as the leading dash and
    missing transcript evidence shall report measurement incomplete rather than a false zero.
21. While Codex usage tracking is enabled, when its rollout emits cumulative token_count events, the
    Core shall aggregate positive deltas for the parent thread and its native children, separating cached
    input from non-cached input; unrelated sessions and absent evidence shall not be counted as zero cost.
22. While consecutive Actions execute across stages, when the host writes outcomes, coordinator payload
    or Result, it shall use the current Action's `host_execution.work_files` and shall never consume a
    previous Action's handoff file.
23. While Core owns `.ae-state`, when a project state directory is created or reopened, Core shall keep
    its contents out of host workspace diffs without changing the user's root ignore policy or hiding
    business-source changes.
24. While an accepted Result advances away from an Action, when Tick commits, Core shall remove only that
    Action's three ephemeral handoff files; while native Workers are outstanding, the host shall use
    bounded batch waits and shall not poll or reread cumulative diffs every 30 seconds.
25. While Worker outcomes are already journaled but coordinator business fields fail Tick validation,
    when the same active Action is repaired, the assembler shall reuse immutable Worker facts and issue a
    new Result identity; any Worker-fact change shall remain a journal conflict.
26. While a Codex session exposes a supported native Worker tool family under any registered namespace,
    when a spawn Action is mapped, the host shall select the first complete exposed spawn/wait/close family,
    preserve fresh-context and bounded-wait semantics, and shall not report capability unavailable because
    one legacy tool name is absent.
27. While a terminal lease still identifies an EventStore thread after active checkpoint release, when
    status is requested, the CLI shall return that terminal projection without traceback; while token
    usage is nonzero but LOC evidence is absent, M5 shall report measurement incomplete rather than a
    misleading complete zero ratio.
28. While Developer has advanced the current batch cursor to a valid component, plate or global completion
    boundary, when StageOffload builds its summary, it shall emit an explicit completion summary without
    calling an out-of-range current-batch accessor or logging a degraded-state warning.
29. While a design-driven thread is still in pre-Architect Gap Scan or Gap Review, when a new host session
    resumes it, compatibility shall bind the current design to the init-persisted digest or the Core-issued
    active Action ledger digest and shall not require a not-yet-created architecture baseline.
30. While an in-flight Action crosses an installed Build boundary, when its accepted Result activates the
    pending Runtime Revision, TickKernel shall emit the dedicated RuntimeRevisionActivated event in the
    same atomic commit and shall never encode or reject it as an unmapped generic projection delta.
31. While Gap Review carries a Core-generated `auto_decision`, when a host finalizes its coordinator
    payload, the Finalizer shall bind gap, resolution, source and policy from the active Action while
    preserving only host-supplied explanatory fields; host omission or mutation shall not alter policy.
32. While a recovering host submits an older Result directly without running Finalizer, when Tick accepts
    the payload, Core shall rebind the same automatic-decision fields before hashing and validation so
    every ingress path preserves the active Action's authority.
33. While a user or authorized thread policy has accepted a Gap Fill, when Architect receives that
    supplement, Core shall label it binding and already approved; Architect shall implement and verify it
    through obligations rather than request approval for the same change again.
34. While the active Action is a Gate associated with a target stage, when its Result is prevalidated or
    ticked, Core shall validate the Gate contract and shall not require the target stage's business payload.
35. While an immutable pre-upgrade Architect Action labels an already-approved supplement as advisory,
    when its Worker redundantly requests the same change, Core shall consume that Result and reissue a new
    Architect Action with binding context, without approving, resetting, or reusing the old Worker.
37. While Gap Scan reports zero gaps, when Core validates the Result, the Result shall bind the active
    design digest and provide one auditable coverage verdict for every Core-parsed design section;
    missing, duplicate, unknown or count-mismatched coverage shall fail closed and reissue Gap Scan rather
    than advance to Architect.
38. While any Gap Scan Result is accepted, when the host continues the run, the next Action shall carry a
    bounded `gap_scan_summary` containing the design digest, covered-section count, gap count and routing
    outcome so both hosts visibly report that the scan occurred; a zero-gap summary is informational and
    shall continue automatically.
39. While Gap Scan finds a design-semantic, architectural or public-contract choice, when Core routes the
    next Action, it shall emit `gap_review` with `WAIT_USER`; only an explicit current-gap decision or a
    previously granted structured `apply_to_remaining=recommendations` policy may continue. Project
    mechanics already proven by ProjectProfile shall not create a user decision.
41. While `remaining_recommendations` is active, when a Gap recommendation lacks
    `requires_user_approval=false` or marks a binding design impact, Core shall keep `WAIT_USER` and
    reject a forged `thread_policy` Result.
42. While a project declares a browser E2E command, when ProjectProfile is resolved, the Action shall
    expose a read-only browser capability preflight with available alternatives or
    `BROWSER_RUNTIME_MISSING`; the preflight shall not download drivers or classify an unrun E2E as a
    Core/product failure.
40. While an active Gap Scan coordinator artifact is missing, stale or bound to another Action, when the
    host resumes or finalizes, it shall regenerate the current Action-scoped result or return a recoverable
    protocol error; it shall never substitute `gaps=[]`, zero evidence or a previous work file.
36. While the active spawn Action already has a committed Core-owned outcome journal, when any host session
    resumes or remaps that Action, the host projection shall set `spawn_permitted=false`, restore immutable
    outcomes and Result, and allow Result submission or coordinator-only repair without another Worker.
37. While a project has an active thread, when status is queried or Tick is mistakenly invoked without a
    Result, the CLI shall return the same structured `resume_active_action` operation and thread identity;
    Tick shall remain fail-closed and no host shall scan state files to infer the active Action.
38. While strict Worker outcomes are requested, when Action instruction, Skill, Command and Assembler define
    their shape, every source shall require the same isolation evidence field and no valid native execution
    shall need a manual JSON repair.
39. While Architect emits a TDD batch plan, when task dependencies and obligations are validated, tests shall
    precede and remain independent of paired implementation tasks, implementations shall depend on those tests,
    and every verification target shall resolve to a dedicated test or contract-test task.
40. While an Architect Result fails deterministic plan initialization, when its repair budget remains, Core
    shall preserve the prior state, record the retry fact, and issue a new Architect Action with exact feedback;
    after two failed repairs it shall fail closed instead of retrying indefinitely.
41. While active spawn Action 的原生 Worker 已返回超时或失败事实，when 宿主终结本轮执行，
    HostExecutionAssembler shall 以该 Action 身份和不可变 outcome 原子生成 `spawned=false` 的失败
    Result，并将 journal 标为可重试的 `worker_failed`，不得生成成功 proof、receipt、attestation
    或采用 coordinator 业务载荷；when Core 接收规范的 `HOST_WORKER_TIMEOUT`，the Loop shall 保留
    active Action 和业务修复预算并返回 `WAIT_RESOURCE`，下一次 init 允许按原 Action 有界重试。
42. While 同一 active Action 的 Worker 连续超时，when Assembler 终结原生 `timeout` 或
    `timed_out` 状态，the journal shall 原子递增 `spawn_retry_attempt`；Core shall 只在第 1 次
    超时返回自动 `WAIT_RESOURCE`，第 2 次返回 `HOST_WORKER_TIMEOUT_EXHAUSTED`，不得形成无限
    Worker 重启或把宿主网络故障计入业务计划修复预算。

## 7. 2026-08-30 真跑闭环补充规则

本节把本次真实运行暴露的“宿主已经退出、Core 仍要求继续”定义为产品级协议错误，
不再把它当作某个 CLI 参数或某个字段的局部问题。

1. **唯一终态出口**：`HostSupervisor` 返回前，最终 Action 必须是
   `WAIT_USER`、`WAIT_RESOURCE`、`HANDOFF`、`TERMINAL` 或 `ERROR`。若仍是
   `CONTINUE`，必须生成稳定的 `HOST_SUPERVISOR_PROTOCOL_ERROR`，禁止静默把控制权交还宿主。
2. **租约生命周期**：从 Action 投影成功到本次 Supervisor 返回，`HostRunLease` 只表示
   当前调用正在履行执行义务。Supervisor 成功、等待、能力预检失败或异常退出时都必须
   关闭本次租约；下一次真正返回 `CONTINUE` 的 Action 再建立新租约。租约不是跨调用的
   任务队列，也不是恢复事实源。
3. **结果合同单一来源**：Coordinator 的字段白名单、必填项和类型只来自当前 Action 的
   `result_contract`。`expected_format` 仅用于提示和旧版本回退，不能覆盖或缩小机器合同。
   Research 正常结果、搜索不可用结果和错误诊断必须通过同一 Finalizer/Validate/Tick 链。
4. **拒绝后的同 Action 修复**：Result 被 Core 拒绝时，修复只能重开 Coordinator 的
   fresh context，复用已固化的 Worker outcome journal；必须再次执行
   `finalize → validate → submit`，不得重新创建已经完成的 Worker，也不得由宿主手写
   身份字段或共享证明。
5. **纵向门禁优先**：L1 函数测试不能关闭上述产品风险。至少一条黑盒轨迹必须覆盖
   `init → Worker/inline → Result rejection → 同 Action repair → validate → tick →
   下一 Action/等待/终态`，并断言 lease、工作文件、Outcome Journal、EventStore 和
   Stop Report 的最终状态。缺少该轨迹时，版本只能称为“组件可测”，不得称为可真跑。
