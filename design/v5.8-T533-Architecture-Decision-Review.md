# T533 Action-scoped Supervisor 架构决策评审

> 状态：2026-08-23 用户已批准。D13 修订为“工程线程连续、宿主模型上下文按 Action
> 隔离且自动续作”；`v5.8-Action-Scoped-Host-Context-Spec.md` 成为实施规格。

## 1. 决策结论

推荐方案 B：保留一个长期、确定性的 `EngineeringThread`，但不再保留一个长期增长的
LLM 宿主会话。产品层 `HostSupervisor` 对每个 Canonical Action 创建一次全新、无历史
transcript 的宿主执行上下文；该上下文只完成当前 Action，写入受 Action identity 绑定的
work files 后退出。Supervisor 校验、finalize、submit 并取得下一 Action，直到终态或真正的
用户/资源等待。

这不是“每个 Tick 让用户重新启动”，也不是把状态交给摘要。用户仍只发起一次命令；
Core 的 EventStore、Checkpoint、ArtifactRef、Action identity 和恢复协议仍是唯一事实源。

## 2. 为什么必须进入架构决策

- T530 已把 Developer 迁移为 fresh Worker，T531 已限制 Worker outcome，T536 已把宿主
  操作改成 Core 下发的机器 argv；固定会话可到达 `GOAL_ACHIEVED`。
- 同 Build Codex 真跑末两段仍分别产生约 2.44M/2.33M cached 和
  1.35M/1.28M cached。说明业务 Prompt 已缩小，但外层长期会话仍反复携带历史。
- 继续删除 Prompt 字段、减少审计角色或依赖 compaction，只能改变波动，不能消除历史
  重放机制；并会破坏独立 Critic、审计和可追溯性。

## 3. 与原始设计的关系

| 原始不变量 | 方案 B 如何保持 |
|---|---|
| 确定性状态与宿主会话解耦 | Thread/事件/检查点长期存在；host context 只是短生命周期执行器 |
| 用户一次启动、自动续作 | Supervisor 内部循环，无人工 continue 或交接命令 |
| 独立 Architect/Developer/Critic/审计 | 各 Worker 仍是独立上下文，不合并角色、不回灌完整输出 |
| 恢复不依赖聊天历史 | 新 context 只读取 Canonical Action、内容寻址引用和当前 work files |
| 不按 Tick 数猜测上下文 | 只以 Action identity 切分，不使用 Tick 阈值或 token 估算触发 |
| 宿主无关 | Core 不调用 Codex/Claude；HostInvocation backend 封装宿主差异 |

## 4. 业界模式核对

- Durable execution 的通行做法是把持久状态放在 checkpoint/thread，把一次节点执行当作
  可重试单元；失败后从已提交边界恢复，而不是依赖进程内对话。
- LangGraph 官方将 per-invocation 作为大多数独立 subagent 调用的推荐模式：父图持久化，
  子调用每次从新状态开始。
- 本机 Codex 已提供 `codex exec --ephemeral -C --json --output-schema`；本机 Claude Code
  已提供 `claude -p --no-session-persistence --output-format stream-json`、进程超时和
  `--max-budget-usd`。这些能力支持一次性执行，但是否允许插件内嵌套必须先 probe，禁止绕过
  宿主保护变量。

参考：
[LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence) ·
[LangGraph subgraphs](https://docs.langchain.com/oss/python/langgraph/use-subgraphs) ·
[LangGraph runtime positioning](https://docs.langchain.com/oss/python/concepts/products)

## 5. 方案比较

| 方案 | 正确性 | 成本可控性 | 复杂度 | 结论 |
|---|---:|---:|---:|---|
| A. 固定长会话继续压缩 | 已证明可终态 | 已证明失败 | 低 | 不推荐 |
| B. Action-scoped Supervisor | 保持 Core 语义 | 从机制上阻断历史重放 | 中 | 推荐 |
| C. 每 Tick/预算阈值换会话 | 容易把执行节拍误当状态边界 | 不稳定 | 高 | 禁止 |

## 7. EARS 批准门槛

1. While 一个工程线程含多个 Action, when Supervisor 执行下一 Action, the product shall
   创建不含上一 Action transcript 的全新 host context，并保持同一 Core thread identity。
2. While Action context 成功退出, when Supervisor 提交 Result, the Core shall 校验 exact
   action/build/root identity 后才推进一次 Tick。
3. While backend 不可用或禁止嵌套调用, when capability probe 执行, the product shall 返回
   `HOST_ACTION_CONTEXT_UNAVAILABLE`，不得静默降级为长期上下文。
4. While context 在任意 journal 边界崩溃, when Supervisor 恢复, the product shall 复用已提交
   outcome，且不得重复 spawn 已完成 Worker。
5. While frozen Canary 运行, when 到达终态, the release gate shall 同时验证语义终态、预算、
   安装来源隔离和无开发目录访问；任一失败继续阻断发布。

## 8. 明确不做

- 不删除 Critic、系统审计或多角色隔离来换 token。
- 不把 recap、聊天摘要或完整 EventStore 注入新 context。
- 不恢复固定 Tick 数、软 token 阈值或人工会话交接。
- 不在 capability probe 失败时偷偷执行当前外层长会话。
- 不把本次批准扩大为削减审计、绕过宿主保护或改变 Core 确定性语义。

### TDD 顺序

1. RED：schema 拒绝旧 transcript、自由文本 recap、越界路径和不匹配 identity。
2. GREEN：只实现 Request/Receipt 值对象与序列化，不接宿主进程。
3. RED：fake backend 证明连续多个 Action 必须获得不同 context identity。
4. GREEN：Supervisor 驱动 fake backend 到终态，并保持连续模式语义轨迹等价。
5. RED：probe 不支持、超时、退出码异常、prepared journal 崩溃和陈旧 Result。
6. GREEN：实现 fail-closed、取消和幂等恢复，不进行无界重试。
7. RED/GREEN：分别实现 Codex、Claude argv/backend 契约；外部模型调用只在真实 Canary。
8. 最后执行专项、全量、静态门禁、打包安装和同 Build 双宿主 L3/L4。

### 测试必须覆盖但当前测试缺失的真实边界

- 外层宿主能否安全启动新的无状态 context，而不继承外层 session identity。
- CLI 实际 stdout/JSONL 中是否含错误、usage、工具事件和最终结构化 Receipt。
- Action N 的 transcript、stdout、work-file path 不得进入 Action N+1 请求。
- context 退出后，只有 Result 被 Core 接受才允许 lease 转移；进程退出本身不是完成证明。
- 开发目录、插件 cache 与内容寻址 release 三者必须区分；运行态只允许后两者中的已安装 release。
- Claude 嵌套保护不允许时必须稳定等待资源，不能删除 `CLAUDECODE` 等环境变量绕过。
