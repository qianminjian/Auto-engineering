# v5.8 主 Agent 协调权恢复与宿主生命周期纠偏设计

> 日期：2026-08-30
> 状态：设计已批准，Phase 85 实施中；L3/L4 真实宿主验收未完成
> 风险：R4 重大架构调整
> 任务：T603-T621
> 替代关系：取代 T533 将 Action-scoped Python Supervisor 设为默认主控的决策；保留 T533 文档和实现作为历史与迁移证据。

## 1. 用人话说明本次改什么

用户启动 Auto-Engineering 后，当前主 Agent 必须一直负责管理 Loop：读取当前 Action、启动和等待独立子 Agent、收集结果、提交 Tick，再继续下一 Action，直到真正需要用户决定、外部宿主不可用或到达 `TERMINAL`。

Python 不再假装管理 Codex/Claude 的原生子 Agent。Python 只负责协议、状态、验证、安全和审计。Architect、Developer、Critic、Verifier、Audit 继续使用独立子 Agent，不能退回主 Agent 直接承担业务工作。

现有 Python Supervisor 不立即删除。第一步只从默认入口旁路，保留回滚能力；Codex 与 Claude Code 的真实 L4 均通过后，才删除过期主控路径。

## 2. 为什么必须调整

### 2.1 原始设计

原始 Thin Coordinator 设计要求：

- 当前主 Agent 是持续 Coordinator；
- 主 Agent 只做 `spawn / wait / collect / finalize / tick`；
- 业务推理和工具执行在独立 Worker 中完成；
- Core 状态不依赖聊天历史。

### 2.2 2026-08-23/24 的错误转向

T533 为解决长会话 token 放大，把默认路径改成：Python Supervisor 为每个 Action 启动一次临时 `codex exec --ephemeral` 或 `claude -p --no-session-persistence` 会话，再由临时会话创建原生 Worker。

该变化实际替换了主控权，属于 R4，而不是普通上下文优化。原批准过程没有用人话说明这一影响，授权范围存在争议。本设计不删除历史，而是以新的明确批准取代旧决定。

### 2.3 已证实的架构缺口

Python 只能管理临时 CLI 进程，不能：

- 保存和等待 Codex/Claude 原生 Worker handle；
- 接收临时 context 退出后的迟到通知；
- 让新 context 接管旧 context 创建的 Worker；
- 在 Claude Code 宿主内可靠嵌套启动另一个 Claude 主会话。

因此旧路径没有单一生命周期所有者。真实运行出现 Worker 已完成、Loop 却因私有 outcome 暂未出现而永久判失败，属于架构必然结果，不是单个 timeout 错误。

## 3. 目标和非目标

### 3.1 目标

1. 用户执行一次设计驱动命令后，主 Agent 自动驱动到合法退出。
2. 当前活跃宿主会话是原生 Worker 生命周期的唯一所有者。
3. Worker 业务结果先原子落盘，通知和聊天文本不作为机器事实。
4. 主 Agent 丢失后只恢复有持久证据的事实，不伪造跨会话接管。
5. token 和费用默认只观测、告警和优化，不阻断流程。
6. 从安装制品公开入口验证真实异步生命周期，不以 Fake Host 代替产品证据。

### 3.2 非目标

- 不回滚 EventStore、Action/Result v1.1、Finalizer、Outcome Journal、Root Lease 和 Coordinator-only repair。
- 不把业务开发重新放回主 Agent inline 执行。
- 不新增用户可见的 `continue`、`resume` 或 `supervisor` 管理命令。
- 不承诺宿主任务彻底终止后插件仍能在对话外自行运行。
- 不优先处理文件长度、命名和历史格式等 P2 整洁问题。

## 4. 风险与影响面

| 类别 | 等级 | 影响 |
|---|:---:|---|
| 主控权 | R4 | 默认主控从 Python Supervisor 返回当前主 Agent |
| 宿主流程 | R3 | Skill/Command 恢复持续 Action 循环，不再默认调用 `--supervise` |
| Worker 生命周期 | R3 | handle 只属于当前活跃宿主会话；落盘 outcome 是唯一可恢复完成事实 |
| 异常恢复 | R3 | 会话彻底丢失时恢复已落盘结果，未落盘 Worker 安全重跑 |
| 跨宿主 | R3 | Codex 与 Claude Code 分别实现原生工具映射，共用机器协议 |
| 预算 | R2 | 默认软约束；只有用户显式配置 hard 才允许预算停机 |
| 迁移 | R3 | Supervisor 先旁路，双宿主 L4 通过后再退役 |
| 用户使用 | R1 | 启动命令和一次启动体验保持不变 |

表中等级表示该决策对产品架构的影响，不表示编辑文档本身的操作风险。Tracker 中 T603-T608 承载已批准的 R4/R3 决策；真正改变运行行为从 T609 开始。

## 5. 目标架构

```text
用户当前主 Agent（唯一 Coordinator）
  ├─ 获取 Canonical Action
  ├─ 持有当前 Action 的原生 Worker handle
  ├─ 启动、等待、回收独立业务 Worker
  ├─ 收集私有 WorkerOutcome
  ├─ 执行 Collector / Finalizer / Validate / Tick
  └─ 持续到 WAIT_USER / WAIT_RESOURCE / ERROR / TERMINAL

独立业务 Worker
  ├─ Architect
  ├─ Developer
  ├─ Critic
  ├─ Component Verifier
  ├─ Plate/System Audit
  └─ 先原子写私有 outcome，再报告完成

Python Core
  ├─ Canonical Action 与 Result 合同
  ├─ EventStore 与状态投影
  ├─ Finalizer、Gate 与 Guardrail
  ├─ Action lease、Outcome Journal 与幂等
  └─ 安全、审计和恢复决策
```

### 5.1 主 Agent 的允许职责

- 消费当前 compact Action 和内容寻址引用；
- 使用当前宿主原生工具启动、等待和关闭 Worker；
- 保存当前 Action 的 Worker ID、handle、状态和 outcome 路径；
- 展示进度和心跳；
- 原样执行 Core 下发的机器操作；
- 丢弃已完成 Action 的业务正文和工具日志。

### 5.2 主 Agent 的禁止职责

- 直接承担 Architect、Developer、Critic 或审计工作；
- 复制完整 Worker diff、日志或报告到主会话；
- 手工制造 native handle、model、隔离证明或 WorkerOutcome；
- 根据聊天通知覆盖 EventStore 或已接受 Result；
- 在新 Action 中复用旧 Action 的 handle 和工作文件。

## 6. Worker 生命周期与所有权

只保留有机器证据的状态：

```text
PLANNED → RUNNING → OUTCOME_COMMITTED → COLLECTED
                   ↘ FAILED
RUNNING + owner context lost + no outcome → OWNER_LOST
```

规则：

1. 单次等待到期只是观察事件，不改变 Worker 状态。
2. 私有 outcome 暂未出现不等于 Worker 失败。
3. Worker 明确失败或 outcome 合同非法才进入 `FAILED`。
4. Worker 先原子写入自己的 `outcome_path`，再发送完成通知。
5. Collector 只汇总实际存在且身份匹配的私有 outcome。
6. 已接受结果不可被重复或迟到通知覆盖。
7. 当前宿主会话是原生 handle 的所有者；Python Core 不宣称持有可跨会话恢复的 handle。
8. 每次 Worker 启动都获得单调递增的 `execution_generation` 和当前 Action lease 的 fencing token；私有 outcome 路径同时绑定二者。

## 7. 异常与恢复

### 7.1 等待到期

- 继续等待并展示心跳；
- 不消耗重试预算；
- 不生成失败 Result；
- 不重启 Worker。

等待轮询与失活判定分离。普通 wait 到期不改变状态；只有以下机器证据之一出现，才允许判定 owner/Worker 已失活：

- 原生宿主查询明确返回 handle 不存在或终态失败；
- 原生取消操作明确确认 Worker 已终止；
- 创建 Worker 的宿主任务/进程身份已经结束或变化；
- Action lease 已过期且原 owner 无法续租。

Worker 在配置的 liveness 观察窗口内没有任何进度时，主 Agent 先查询状态并尝试正常取消；观察窗口不是 token/费用预算，也不能单独构成失败。能确认终止时进入 `FAILED` 或 `OWNER_LOST` 并重试；无法确认旧 Worker 已终止时进入 `WAIT_RESOURCE/WORKER_OWNERSHIP_UNCERTAIN`，保留当前 Action，禁止并发重跑和双写。

### 7.2 Worker 明确失败

- 保留其他已提交 outcome；
- 只重试失败 Worker；
- 重试以新的执行身份运行；
- 同类连续失败才消耗该类重试预算。
- 业务或合同失败不再映射为通用 `WAIT_RESOURCE`；只有宿主资源、所有权不确定或外部限流才进入 `WAIT_RESOURCE`。

### 7.3 Assembler、预校验或 Core 拒绝

- 保留全部 WorkerOutcome 和 fingerprint；
- 只创建 Coordinator-only repair；
- 一次返回全部 violations；
- 禁止重新 spawn Worker。

### 7.4 正常 compaction

若宿主仍属于同一任务和 Agent tree，继续持有原生 handle，Core 状态不变。Codex 与 Claude Code 是否能跨 compaction 保持 handle，必须分别用真实宿主验收，不得由设计假定。

### 7.5 `/clear`、宿主崩溃或任务彻底结束

- 已落盘 outcome：恢复并复用；
- 未落盘 outcome：记为 `OWNER_LOST`；
- 新主 Agent 获取 active Action lease 后重新执行缺失 Worker；
- 旧 Worker 迟到结果使用 Action、worker、execution identity 和 Prompt hash 判定；
- Collector 只接受当前 active `execution_generation + fencing token` 的 outcome；旧 generation 即使先到也只进入审计，不参与当前 Result；
- 当前 generation 的重复同值结果幂等，内容冲突不得覆盖。

### 7.6 外部资源不可用

宿主真实 usage limit、网络或 Agent 容量不足进入 `WAIT_RESOURCE`：

- 保留 active Action 和已完成 outcome；
- 不算业务失败；
- 宿主支持定时唤醒时自动续作；
- 宿主任务已经终止时，在下一次用户或系统唤醒后从原 Action 自动恢复；
- 不承诺在宿主已关闭后插件仍能自行运行。

## 8. 预算和 token 治理

### 8.1 默认软约束

未配置或配置如下时，预算只观测：

```toml
[budget]
enforcement = "soft"
```

- 不因 token、费用、Action 数、Tick 数或运行时长中断；
- 记录 input/cache/output、上下文次数和修复原因；
- 发现重复上下文时告警并形成优化证据；
- 不减少必要的 Critic、Verifier 和 Audit。

### 8.2 显式硬约束

只有用户主动配置 `enforcement = "hard"` 及相应阈值，预算才允许产生等待或停止。外部账户真实限额不属于内部预算，按 `WAIT_RESOURCE` 处理。

### 8.3 成本优化顺序

1. 取消嵌套主宿主反复启动；
2. 业务角色全部 Worker 化；
3. 主 Agent 只保留引用和摘要；
4. repair 不重跑 Worker；
5. 本地确定性归一化机械格式；
6. 再优化模型和审计 fan-out。

流程未跑通前，成本优化不得成为发布完成的替代目标。

## 9. 跨宿主适配

### 9.1 Codex

- 使用当前任务暴露的原生 `spawn_agent / wait_agent / interrupt_agent` 工具族；
- handle 属于当前任务的 Agent tree；
- `/clear`、compaction 和任务恢复后的 handle 可见性必须真实验证。

### 9.2 Claude Code

- 使用当前 Claude Code 会话的 Agent/Task 能力；
- 不再嵌套启动 `claude -p` 作为默认 Action 主控；
- background Agent 完成通知和会话压缩后的可见性必须独立验收。

### 9.3 统一与差异

统一：Action、Worker invocation、outcome schema、Finalizer、EventStore、恢复规则。
差异：原生工具名、handle 类型、等待语义、通知和宿主唤醒能力。工具差异由宿主 Skill/Command 适配，不进入 Core。

## 10. Supervisor 迁移

1. 第一阶段保留代码，但默认 Skill/Command 不再进入 `--supervise`。
2. 旧 active Action 只在 Action 边界迁移；不修改已经接受的事件和 journal。
3. 迁移期提供明确诊断，禁止同时运行主 Agent Coordinator 和旧 Supervisor。
4. Codex L3/L4 通过后保持旁路状态观察。
5. Claude Code L3/L4 通过后删除旧默认路径、ephemeral backend 和过期文档。
6. 删除属于单独 R3 任务，必须有回滚点和新鲜双宿主证据。

永久保留：T533 决策评审、Action-scoped Spec、Git 历史和相关事故记录，作为授权与架构演进证据。
退役时删除：默认 `--supervise` 路由、仅服务嵌套主会话的 Codex/Claude ephemeral backend、已被新入口取代的执行说明和无调用兼容代码。历史设计文件不得删除或改写为“从未批准”。

## 11. 验收架构

### 11.1 L1 协议单元

验证状态、身份、路径、Result 和预算模式，不证明真实宿主。

### 11.2 L2 异步纵向轨迹

必须使用真实异步进程模拟：第一次等待结束时 Worker 仍运行，随后原子写 outcome；轨迹从公开执行包经过 Collector、Finalizer、Validate、Tick 到下一 Action。测试不得直接制造 completed handle 或读取 Canonical 私有状态补全结果。

### 11.3 L3 安装后宿主 Canary

从 Marketplace 安装制品公开入口执行，至少跨越 Gap、Architect、Developer、Critic，并覆盖一次等待到期和一次同 Action repair。

### 11.4 L4 黄金项目

Codex 与 Claude Code 分别从同一 Build 单命令运行到等价 `TERMINAL`。必须提交安装来源、Action/Worker receipts、EventStore、恢复轨迹和 usage；Fake Host、archive smoke、覆盖率和测试数量不能替代。

## 12. EARS 验收条件

1. While 用户已启动设计驱动 Loop, when active Action 为 `CONTINUE`, the current host Agent shall 持续执行 spawn/wait/collect/finalize/tick，不把单个 Action 结束当作产品结束。
2. While 业务 Action 需要推理或工具执行, when Worker 被创建, the host shall 使用独立原生子 Agent，主 Agent不得 inline 执行业务工作。
3. While Worker 仍在运行, when 一次等待到期或私有 outcome 暂不存在, the host shall 继续等待且不得生成 Worker 失败。
4. While Worker 已原子提交合法 outcome, when Coordinator、Assembler 或 Core 拒绝 Result, the system shall 复用该 outcome 并只修复 Coordinator。
5. While owner context 已彻底丢失, when 新主 Agent 恢复 active Action, the system shall 复用已落盘 outcome，并只对未落盘 Worker 以新执行身份重跑。
6. While a replacement Worker is active, when an older execution writes a late outcome, the Collector shall reject it from the active Result unless its `execution_generation` and fencing token equal the active lease; rejected evidence shall remain audit-only。
7. While budget 未显式配置为 hard, when token、费用、Action 数或运行时间超过观测阈值, the system shall 记录告警并继续，不得中断 Loop。
8. While 外部宿主返回真实资源限额, when Runtime 保存等待状态, the system shall 保留 active Action 和已完成事实；宿主定时器或下一次入口唤醒后，`status.next_operation` shall 指向同一 active Action 的恢复操作。
9. While 当前入口已采用主 Agent Coordinator, when 双宿主 L4 尚未全部通过, the repository shall 保留旧 Supervisor 作为旁路兼容且不得宣称其已退役。
10. While 候选版本准备发布, when 任一双宿主 L4、安装来源或真实异步恢复证据缺失, the release shall remain blocked。
