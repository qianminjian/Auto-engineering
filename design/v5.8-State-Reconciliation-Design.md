# v5.8 状态冲突诊断与任务续作设计

> 日期：2026-08-09｜阶段：Phase 81｜状态：已批准，待实施
> 目标：用户只需提交设计文档；旧状态与当前项目冲突时，由系统先咨询用户，再安全地重新初始化或修复状态续作。

## 1. 用户问题

用户执行：

```text
$auto-engineering --design-doc design/example.md
```

`/clear` 只清理宿主聊天，不删除项目隐藏目录。项目内 `.ae-state/events.db` 和
`.ae-state/checkpoints.db` 可能继续保存未完成 thread、计划和 active Action。当前 Skill
只要发现 active thread 就优先恢复，导致本次明确传入的设计文档没有成为启动决策的最高
优先级输入。

用户不应了解 thread、checkpoint 或 `.ae-state` 的内部结构，也不应被要求手动删目录。

## 2. 已证实故障

1. 测试项目 `.ae-state/events.db` 同时保留两个 thread。
2. thread `fa9c5495-2b78-4889-ad08-56b8446299b2` 的 Projection 为
   `stage=developer`，active Action 为 `batch=B2`。
3. 用户清理聊天并再次显式传入设计文档后，宿主仍恢复该 B2。
4. 项目可见源码和 `package.json` 已与旧计划不一致，但旧
   `.ae-state/init-manifest.json` 仍使 ProjectProfile 被判为可恢复。
5. Developer 随后在错误计划上创建孤立文件，并以文件 smoke 替代业务测试。

## 3. 设计原则

| ID | 原则 |
|---|---|
| SR-I1 | 用户本次显式输入高于历史自动恢复偏好，但不直接删除历史事实 |
| SR-I2 | 状态一致时继续自动续作，不为正常恢复增加询问 |
| SR-I3 | 状态冲突时先询问，未取得选择前禁止 Agent 写项目文件 |
| SR-I4 | “重新初始化”逻辑关闭旧 thread 并保留审计，不物理删除 `.ae-state` |
| SR-I5 | “修复状态并续作”保留可验证完成事实，失效任务只标记 superseded，不改写历史 |
| SR-I6 | ProjectProfile 声明不等于当前项目可执行；legacy manifest 不能单独证明项目仍存在 |
| SR-I7 | 业务任务必须由真实业务测试验证，文件存在 smoke 只适用于显式 setup/documentation task |
| SR-I8 | Claude Code 与 Codex 对相同事实必须提出相同选择并产生等价 Core 事件 |

## 4. 启动语义

### 4.1 未显式传入设计文档

```text
$auto-engineering
```

- 有兼容 active thread：自动恢复。
- 无 active thread：要求提供设计文档或需求。
- active thread 状态损坏：返回稳定错误，不猜测恢复。

### 4.2 显式传入设计文档

```text
$auto-engineering --design-doc design/example.md
```

Core 必须先建立 `InvocationIntent`：

```json
{
  "mode": "design_doc",
  "design_doc_path": "design/example.md",
  "design_doc_digest": "sha256:...",
  "scope": null
}
```

然后比较当前项目事实与 active thread：

| 状态 | 行为 |
|---|---|
| 无 active thread | 初始化新 thread |
| active thread 与设计文档、项目锚点和执行计划一致 | 自动续作 |
| active thread 与任一关键事实冲突 | 发出状态协调 Gate，禁止恢复旧 Action |

显式 `--design-doc` 不等于每次强制重开；它表示“以这份设计文档和当前项目为准”。

## 5. 有界一致性检查

新增只读 `StateCompatibilityInspector`，不得递归扫描整个项目。输入：

- InvocationIntent；
- active thread Projection 与 Action Snapshot；
- 当前设计文档摘要；
- 当前 ProjectProfile 证据；
- 固定工程锚点：package manifest、lockfile、语言配置；
- Profile 声明的 source/test roots 是否存在；
- active Action 的目标文件存在性和已记录摘要（若有）。

输出：

```json
{
  "status": "compatible|conflict|corrupt",
  "reason_codes": [],
  "old_thread_id": "...",
  "old_design_digest": "...",
  "current_design_digest": "...",
  "missing_anchors": [],
  "changed_roots": []
}
```

`conflict` 至少包括：

- 用户指定了不同设计文档；
- 同一设计文档内容已变化；
- 旧 Profile 依赖的工程入口或源码根消失；
- 当前项目类型与旧 Profile 不一致；
- active Action 的任务基线无法在当前项目中解释。

legacy init manifest 只能作为兼容提示，不能覆盖当前入口文件缺失事实。

## 6. 用户协调 Gate

复用现有 `gate` Action 和 `ExecutionControl.WAIT_USER`，不新增管理命令：

```json
{
  "action": "gate",
  "gate": {
    "id": "state_reconciliation",
    "type": "decision",
    "prompt": "检测到旧开发状态与当前项目不一致，请选择处理方式。",
    "options": [
      {"id": "reinitialize", "label": "重新初始化"},
      {"id": "reconcile", "label": "修复状态并继续"}
    ]
  },
  "execution_control": {
    "disposition": "WAIT_USER",
    "reason_code": "STATE_RECONCILIATION_REQUIRED"
  }
}
```

宿主必须直接展示两个选择，不得由 Agent 替用户选择。无 TTY 或无法交互时原样返回 Gate，
不默认恢复、不默认清理。

## 7. 选择一：重新初始化

`reinitialize` 的语义：

1. 追加 `ThreadSuperseded`，reason=`user_reinitialize`。
2. 关闭旧 active lease 和 Action；保留 Event、Result、Artifact 和日志。
3. 使用当前 InvocationIntent 创建新 thread。
4. 重新解析设计文档和当前项目。
5. 当前项目只有设计文档时，正常进入 `project_setup_required`。
6. 重新生成 ArchitectureBaseline、batch plan 和进度投影。

禁止：

- 删除 `.ae-state`；
- 覆写或迁移旧 thread 的 Event；
- 把旧完成任务复制为新 thread 的完成事实；
- 恢复旧 active Action。

## 8. 选择二：修复状态并继续

`reconcile` 不直接修改旧计划，而是进入只读 `PLAN_RECONCILE`：

1. 读取当前设计文档、当前项目、旧 ArchitectureBaseline 和任务状态。
2. 对旧任务分类：`verified_completed`、`still_pending`、`superseded`、`unverifiable`。
3. `verified_completed` 必须有文件和 Gate 证据与当前项目匹配；仅旧状态标记不够。
4. 失效任务保留历史 ID 并标记 superseded，不能删除或改写为未发生。
5. 新需求和失效任务使用新 batch/task ID。
6. 生成新的 Architecture revision 和 Current Work Set。
7. 用户无需再次逐任务确认；候选通过 Core 校验后自动进入正确的下一任务。

`PLAN_RECONCILE` 与 `PLAN_REFINE` 分离：后者只允许增量修复，不能表达设计变化、项目重置
和任务失效；强行复用会再次产生 PlanPatch 冲突。

## 9. 状态跟踪投影

进度统计只计算当前 Work Set，同时保留历史：

```json
{
  "plan_revision": 3,
  "current": {
    "total": 12,
    "completed": 5,
    "pending": 7
  },
  "historical": {
    "superseded": 4,
    "unverifiable": 2
  },
  "reconciled_from_revision": 2
}
```

公共 status 必须说明：

- 当前 thread 和 plan revision；
- 是否由旧状态协调而来；
- 保留了多少已验证完成任务；
- 多少旧任务被 superseded；
- 下一项真实待办。

不得再出现旧 B2 已失效但 status 仍显示 B2 为 active 的情况。

## 10. 验证证据边界

本次事故同时证明 Developer 自报计数不可作为权威测试证据：

- `test_results` 是 Agent claim；Core Gate 的真实命令、退出码和文件摘要才是事实。
- `implementation/test/contract_test` task 不接受文件存在或 JSON 合法 smoke。
- smoke 仅适用于显式 `project_setup`、`configuration` 或 `documentation` task。
- Contract 静态字符串扫描只作辅助 finding；权威通过必须来自可执行 contract test。
- 环境或 manifest 缺失属于 `environment_failure`，不得路由为代码修复循环。

## 11. 事件与状态

新增领域事件：

- `StateConflictDetected`
- `StateReconciliationSelected`
- `ThreadSuperseded`
- `PlanReconciled`
- `TaskSuperseded`

选择 Result 必须绑定 Gate message ID，重复提交幂等。所有选择、分类、旧新 revision 映射
必须可由事件重放；不得通过修改 checkpoint JSON 偷换状态。

## 12. 失败处理

| 失败 | 处理 |
|---|---|
| 协调 Gate 未选择 | 保持 WAIT_USER，不写项目 |
| 旧 Event/Projection 损坏 | `STATE_CORRUPT`，只允许重新初始化或导出审计 |
| reconcile 无法验证任何完成项 | 提示结果并按当前设计生成全新 Work Set，历史仍保留 |
| 新项目能力不足 | `project_setup_required`，不是 Developer retry |
| 用户选择重复提交 | 返回首次选择结果，不重复创建 thread/revision |
| 宿主中断 | 恢复同一协调 Gate，不重新询问不同问题 |

## 13. 禁止项

- 禁止把 `/clear` 当作清理 Loop 状态。
- 禁止要求用户手动删除 `.ae-state` 才能重启。
- 禁止发现 active thread 就无条件恢复。
- 禁止显式设计文档被历史 active Action 静默覆盖。
- 禁止自动物理删除旧状态。
- 禁止用 PLAN_REFINE 伪装状态协调。
- 禁止用 smoke 替代业务测试。
- 禁止因“全自动”而替用户选择清理或续作。

## 14. EARS 验收

1. While 无 active thread, when 用户显式提交设计文档, the system shall 创建新 thread。
2. While active thread 与当前设计和项目一致, when 用户提交相同设计文档, the system shall
   自动续作且不额外询问。
3. While active thread 与当前项目冲突, when 用户显式提交设计文档, the system shall 在任何
   项目写入前返回重新初始化/修复续作二选一 Gate。
4. While 用户选择重新初始化, when Gate Result 被接受, the system shall 保留旧审计、逻辑
   关闭旧 thread 并按当前设计创建新 thread。
5. While 用户选择修复续作, when reconcile 完成, the system shall 保留可验证完成项、标记
   失效任务并生成当前 Work Set。
6. While `.ae-state/init-manifest.json` 存在但 package/source roots 消失, when compatibility
   inspection 运行, the system shall 判定 conflict，不得恢复旧 Developer Action。
7. While 业务 task 只提供文件 smoke, when Developer Result/Gate 校验, the system shall
   拒绝其作为业务测试通过证据。
8. While Claude Code 与 Codex 处理相同冲突轨迹, when 用户选择相同选项, both hosts shall
   产生等价事件、当前任务和 status。
9. While 协调选择被重复提交或进程中断, when 恢复运行, the system shall 幂等返回同一结果。

## 15. 发布门禁

Phase 81 完成前不得生成下一 RC。门禁至少包括：

- 隐藏 `.ae-state` + 可见项目被清空的黄金轨迹；
- 同设计兼容自动续作；
- 设计变化后二选一；
- reinitialize 审计保留与新 thread；
- reconcile 完成事实验证、superseded 和新 Work Set；
- smoke 伪测试拒绝；
- 双宿主交互等价；
- 全量、覆盖率、静态、事件重放、故障注入和真实产品安装验收。
