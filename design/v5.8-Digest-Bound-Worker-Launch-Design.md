# v5.8 Digest-Bound Worker Launch 设计

## 问题与证据

T525 已让 CLI 不再内联 Worker Prompt，但真实 Codex L3 仍由 Coordinator 先读取
`prompt_ref`，再把完整正文作为 `spawn_agent` 参数发送。于是正文同时进入工具调用、工具结果和
主会话历史，compact envelope 只能把外层 input/cache 从 5.01M/4.85M 降到
3.29M/3.05M，未消除数量级放大。

## 决策

保留 D13：Core ExecutionSession 和用户启动保持连续，不用换会话掩盖重复输入。Host Adapter
为每个 invocation 生成有界 `native_launch_prompt`，只包含：

- 固定 `project_root`；
- 相对项目根的 `prompt_ref` 与 `prompt_sha256`；
- “由 Worker 自己读取并校验正文”的操作；
- `may_drive_loop=false`、`may_spawn_workers=false` 权限边界。

Coordinator 必须把该字段原样作为原生 spawn 工具输入，不得先读取、复制、总结或重新拼接
Worker Prompt。Worker 在 fresh context 中读取正文；业务 Result、receipt、attestation 和
outcome journal 仍按原协议生成。Canonical Action 与 Prompt Artifact 均不改变。

## 安全与兼容

- launcher 由 Adapter 从已校验的 SpawnPlan 生成，宿主不得接受用户提供的替代 launcher。
- `project_root` 必须来自 Action 机器事实；Prompt hash 仍由 Worker 在读取前校验。
- launcher 不携带业务上下文，长度应有界；未知 shell 的完整 Action 兼容路径不受影响。
- 旧宿主忽略新字段时协议仍可运行但不满足产品成本门禁，发布验收必须捕获该漂移。

## EARS 验收

1. While a mapped spawn Action is emitted, when Host Adapter builds worker execution facts,
   the adapter shall provide one bounded `native_launch_prompt` per invocation containing the
   exact root, ref and digest but no Worker Prompt body.
2. While Codex or Claude executes a spawn Action, when it calls the native worker tool, the
   coordinator shall pass `native_launch_prompt` verbatim and shall not read `prompt_ref` first.
3. While the Worker receives the launcher, when it opens the artifact, the worker shall verify
   SHA-256 before following the prompt and shall not drive Loop or spawn another Worker.
4. While dual-host L3 is evaluated, when either terminal or cost evidence fails, the release
   gate shall remain blocked and D13 shall not be flipped implicitly.

## 实测结论

T528 Codex L3 的四次 native launch 均为 533 bytes，机制按设计生效；但四个 fresh Worker
各自加载宿主基础上下文，最终 cache read 反而达到 10.48M。Launcher 是必要的协议修正，
不是完整成本方案。下一阶段必须减少小项目重复启动的验收 Worker 数，而不是重新内联 Prompt、
取消独立审查或只更换计费更低的模型。
