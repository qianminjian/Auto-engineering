# v5.8 真实宿主 L3/L4 验收 Runbook

> 状态：执行手册，不是自动验收替代品。只有真实 Codex/Claude Code 原生会话产生的证据，
> 才能关闭 T619/T620 和 A008。

## 1. 目标与硬边界

本手册验证同一个 Release Build 在 Codex 与 Claude Code 中是否能够从一次用户入口连续运行
到等价 `TERMINAL`。`archive smoke`、Fake Host、自动化测试和手工拼接 JSON 均不能代替
L3/L4。

执行时必须满足：

1. 两个宿主使用同一个 `build-info.json` 的 `build_id`。
2. 每个宿主使用全新的项目目录、全新的原生会话和全新的 `.ae-state`。
3. 安装来源是宿主原生 Marketplace；开发目录不得成为运行时或插件来源。
4. 主 Agent 是唯一 Coordinator；Worker 通过原生独立上下文执行，不能嵌套另一个 Loop。
5. `CONTINUE` 必须继续消费下一 Action；只有 `TERMINAL`、`ERROR` 或明确交接状态才能结束。
6. 任何手工修改 outcome、receipt、proof、Result 或 EventStore 的行为都使本次证据失效。

## 2. 候选制品和预检

在仓库根目录执行，先保存制品身份，不要重新从开发目录构建另一个包：

```bash
ARCHIVE=/absolute/path/to/release.tar.gz
REPO_ROOT=/absolute/path/to/Auto-engineering
STAGING_ROOT=/tmp/ae-a008-staging
WHEEL_CACHE=$(uv cache dir)
EVIDENCE_ROOT=/tmp/ae-a008-evidence
CODEX_PROJECT_ROOT=/tmp/ae-a008-project-codex
CLAUDE_PROJECT_ROOT=/tmp/ae-a008-project-claude
# L4 预算是验收策略，不是 Loop 的驱动器；按本次真实轨迹显式声明并留档。
CLAUDE_COST_LIMIT_USD=40

tar -xOzf "$ARCHIVE" plugins/auto-engineering/build-info.json
uv run python scripts/install_acceptance.py \
  --archive "$ARCHIVE" --host codex --wheel-cache "$WHEEL_CACHE"
uv run python scripts/install_acceptance.py \
  --archive "$ARCHIVE" --host claude-code --wheel-cache "$WHEEL_CACHE"
```

上述命令只证明归档包完整和内部入口可用。输出中的 `product_install` 必须仍是
`not_run`；不能把它当作 L3/L4 通过。

在每个宿主的 Marketplace 安装完成后、启动任何 Loop Action 之前，必须使用该宿主实际
加载的插件入口执行只读身份预检。先把第 2 节归档包中的 `build_id` 保存为
`EXPECTED_BUILD_ID`，再将安装器报告的插件根目录保存为 `PLUGIN_ROOT`，让该入口做强制比较：

```bash
EXPECTED_BUILD_ID=$(tar -xOzf "$ARCHIVE" plugins/auto-engineering/build-info.json \
  | uv run python -c 'import json,sys; print(json.load(sys.stdin)["build_id"])')
"$PLUGIN_ROOT/bin/ae-run" build-info --expect-build-id "$EXPECTED_BUILD_ID"
```

上述预检命令必须从目标项目根执行（分别是 `CODEX_PROJECT_ROOT` 或 `CLAUDE_PROJECT_ROOT`），
不能从插件根目录执行。插件根是只读发布资产，
`ae-run` 可能需要在当前项目创建 `.ae-state/.ae-runtime`；从插件根启动会把运行时状态
错误地写入发布目录并应当被系统拒绝。真实宿主启动时必须把该根规范化后导出为
`AE_INVOCATION_PROJECT_ROOT`；任何后续 runner 请求偏离它都必须以
`AE_PROJECT_ROOT_DRIFT` fail-closed，不能切换到另一个项目继续。

若命令非零退出，或输出的 `version`、`source_kind` 与候选制品不一致，立即停止本次验收；
不得继续运行、手工修复协议或把旧缓存的结果计入新 Build 证据。只有身份一致后，才能
执行第 4 节的真实宿主 Canary。

## 3. 安装同一 Build

两个安装动作都必须指定 `--archive`。`--source` 只用于日常开发安装，不属于发布证据。
安装器会调用宿主原生 Marketplace，并在安装后校验 Build Identity 和项目运行时隔离。

```bash
uv run python scripts/install_codex_local.py \
  --archive "$ARCHIVE" \
  --root "$REPO_ROOT" \
  --staging-root "$STAGING_ROOT/codex"

uv run python scripts/install_claude_local.py \
  --archive "$ARCHIVE" \
  --root "$REPO_ROOT" \
  --staging-root "$STAGING_ROOT/claude"
```

安装后必须记录：宿主报告的 Marketplace 根、插件根、插件内 `build-info.json`、插件
Python import origin、项目 `.ae-state/.ae-runtime` 和本次 `build_id`。插件树应保持只读，
运行时只能位于目标项目。

## 4. L3 Canary：最小真实连续轨迹

Codex 使用 `$auto-engineering`；Claude Code 使用 `/auto-engineering:dev-loop`。两个宿主
分别在新项目中执行同一份 Canary 设计，不能使用 `scripts/ae-run --init` 代替宿主入口。
`scripts/ae-run` 只由宿主 Skill/Command 作为 Core 协议桥接调用。

Canary 至少覆盖：

- `Architect → Developer → Critic` 三个阶段；
- 一次真实 Worker wait，wait 到期不被改写为失败；
- 一次同 Action 恢复或 Coordinator repair；
- 原生 Worker outcome、attestation、receipt、EventStore 和下一 Action 的完整因果链；
- 无手工协议修复、无意外停止、无 Worker 递归、无跨 Action 路径复用；
- 最终 Core 结果明确区分 `TERMINAL` 与产品验收边界。

L3 失败时只记录失败类别和原始证据，不延长 Tick、重复启动旧 Worker 或手工修复后继续。

非交互或需要捕获原始 `stream-json` 的 Claude 运行必须使用宿主进程边界适配器，避免
预算耗尽、硬限制或 CLI 直接退出绕过 Claude 生命周期 Hook：

```bash
HOST_OUTPUT="$CLAUDE_PROJECT_ROOT/claude-stream.jsonl"
"$PLUGIN_ROOT/scripts/ae-host-run" \
  --project-root "$CLAUDE_PROJECT_ROOT" \
  --output "$HOST_OUTPUT" \
  --max-runtime-seconds 1800 \
  -- claude -p --output-format stream-json --verbose \
  '/auto-engineering:dev-loop "执行设计驱动工程闭环，严格遵守 Action 合同。"'
```

该适配器只保存宿主原始输出并在进程退出后记录 Stop Report，原退出码原样返回；它不发起
任务、不读取或改写业务 Result、不推进 Tick。若直接调用 `claude -p`，Hook 只能视为尽力
而为，硬预算/硬限制退出可能在 Hook 执行前结束，不能作为 L3/L4 的可追溯入口。

## 5. L4 Voice Clone 黄金项目

只有双宿主 L3 均通过后才执行 L4。L4 使用同一份 Voice Clone 设计摘录、同一候选
`build_id` 和两个全新项目，验证完整的：

`Architect → Gap/Approval → Developer → Critic → Verification → TERMINAL`。

除 Loop 轨迹外，还必须单独记录业务边界：真实 API、上传、浏览器、设备权限和最终
`typecheck/unit_test/build` 的已验证项与未验证项。Core 的 `TERMINAL` 不能替代这些业务
证据；任何未经批准的设计升级（例如把 BFF future 提前为 V1）都阻断发布。

## 6. 证据包和发布校验

每个宿主至少提交一个内容寻址 evidence artifact，并在外层证据中绑定：

- `host`、候选 `build_id`、全新 `project_state`；
- `installation.source_kind=marketplace`、非空 `source_ref`；
- 与候选 Build 一致的 `source_build_id` 和完整 `source_content_sha256`；
- `build_identity_preflight` 机器事实证明首个 Loop Action 前执行了候选身份比较；
- `semantic_enforcement=full`、`usage_status=complete`；
- 安装发现、Canary 阶段、恢复证明、零意外停止、零手工协议修复；
- Action/Worker receipt、attestation、EventStore 因果链和完整 usage；
- L4 业务 Gate、最终 verdict、设计决策覆盖和未批准变更数量。

业务 Gate 不能通过 collector 参数直接声明。宿主完成真实项目 Gate 后，应使用发布包内的
证据生成器顺序执行明确的 argv，并在项目的 `.ae-state/product-evidence/business-evidence.json`
生成报告：

```bash
uv run python scripts/generate_business_evidence.py \
  --project-root "$CLAUDE_PROJECT_ROOT" \
  --archive "$ARCHIVE" \
  --output "$CLAUDE_PROJECT_ROOT/.ae-state/product-evidence/business-evidence.json" \
  --gate-command 'typecheck=["uv","run","mypy","src","tests"]' \
  --gate-command 'unit_test=["uv","run","pytest","-q"]' \
  --gate-command 'build=["uv","build"]'
```

生成报告的最小格式如下：

```json
{
  "schema_version": "1.0",
  "scenario_id": "voice-clone-v1",
  "build_id": "<candidate-build-id>",
  "gates": {
    "typecheck": {"status": "pass", "command": ["..."], "exit_code": 0,
      "evidence_path": ".ae-state/product-evidence/typecheck.log",
      "evidence_sha256": "<sha256>"},
    "unit_test": {"status": "pass", "command": ["..."], "exit_code": 0,
      "evidence_path": ".ae-state/product-evidence/unit_test.log",
      "evidence_sha256": "<sha256>"},
    "build": {"status": "pass", "command": ["..."], "exit_code": 0,
      "evidence_path": ".ae-state/product-evidence/build.log",
      "evidence_sha256": "<sha256>"}
  },
  "final_verdict": "pass"
}
```

生成器会实际执行每个 argv、保存 stdout/stderr 并计算 hash；Gate 失败时报告为 `fail`，不会
生成可通过的结果。`evidence_path` 必须位于同一项目根内且 hash 与文件当前内容一致。
这是 L4 Golden Project 业务报告，不包含 L3 恢复结论；采集命令必须额外接收独立
`--canary-project-root <path>`，从该项目 EventStore 自动发现 Architect/Developer/Critic
和唯一 canonical recovery projection。两个项目根不能隐式合并，也不能用裸
`--golden-gate`、`--recovery-verified` 或业务报告字段伪造恢复。

校验单宿主证据：

```bash
uv run python scripts/product_acceptance.py \
  --archive "$ARCHIVE" \
  --evidence "$EVIDENCE_ROOT/codex.json" \
  --evidence-root "$EVIDENCE_ROOT" \
  --project-root "codex=$CODEX_PROJECT_ROOT" \
  --max-claude-cost-usd "$CLAUDE_COST_LIMIT_USD"
```

双宿主发布校验：

```bash
uv run python scripts/product_acceptance.py \
  --archive "$ARCHIVE" \
  --evidence "$EVIDENCE_ROOT/codex.json" \
  --evidence "$EVIDENCE_ROOT/claude-code.json" \
  --evidence-root "$EVIDENCE_ROOT" \
  --project-root "codex=$CODEX_PROJECT_ROOT" \
  --project-root "claude-code=$CLAUDE_PROJECT_ROOT" \
  --max-claude-cost-usd "$CLAUDE_COST_LIMIT_USD"
```

只有双宿主返回同一 `build_id` 且 `levels.L3`、`levels.L4` 均为 `pass`，才可关闭 A008。
任何 `not_run`、`measurement_incomplete`、来源不一致、usage 缺失或 artifact hash 失配，
都必须保持发布阻断。

## 7. 失败归属

- 网络、额度、宿主容量或连接中断：记录为环境/资源失败，不能伪造成功，也不能自动把
  `WAIT_RESOURCE` 改成业务失败。
- 插件未发现、Build 不一致、插件树可写、运行时来源错误：安装门禁失败，重新安装同一
  archive 后再开始新的宿主会话。
- Worker outcome、attestation、receipt 或 EventStore 不完整：协议/证据失败，保留原始
  Action 和日志，禁止手工补写共享 proof。
- 设计越权、业务 Gate 失败或最终 verdict 失败：产品 L4 失败，回到设计决策和业务证据
  检查，不以 Core `TERMINAL` 关闭。

## 8. 关闭条件

将两个宿主的原始证据、校验输出、Build Identity、usage 摘要和失败重试记录存入独立
验收目录后，才允许更新 `design/BEACON.md`、`design/IMPLEMENTATION-TRACKER.md` 的
T619/T620/A008 状态。未完成前保持 `v5.8.0-rc.5`，不得生成下一 RC。
