# Auto-Engineering v5.7 渐进式协议内核重构设计

> 状态：已批准，Phase 52 已完成｜批准日期：2026-07-27
> 当前实现基线：`design/v5.6-Design-Loop.md`
> 实施计划：`design/v5.7-Protocol-Kernel-PLAN.md`

## 1. 产品定位

Auto-Engineering 是**跨 Agent 宿主的确定性工程治理内核**：

- 宿主 Agent 负责推理、代码编辑、工具调用和原生子代理调度。
- Auto-Engineering 负责协议、状态、验证、安全、审计和确定性推进。
- Python Core 不调用 LLM，不复制 Claude Code、Codex 或其他宿主的 Agent Runtime。
- 新宿主通过 Host SPI 与版本化 Action/Result 协议接入，不修改 Core 状态机。

本项目不是通用 Agent 框架、模型路由平台或云端多租户调度服务。若未来需要无宿主
运行，应作为独立 Runtime Adapter 产品层接入同一协议，不恢复 Core 内的
StandaloneDriver。

## 2. 问题与成功标准

### 2.1 当前问题

1. 运行时会产生 `gate`、`skip`，但 action schema 未声明，契约测试存在盲区。
2. Result 仅用 `stage` 对齐 Action，无法可靠识别重复、延迟或乱序提交。
3. SQLite 主要保存状态快照，无法证明任意状态都可由不可变事实重放得到。
4. `TickOrchestrator` 同时负责路由、恢复、验证、观测、指标和升级处理。
5. `ActionBuilder` 通过实例字段暂存单次构建上下文，不可重入。
6. HostCapabilities 是静态矩阵，没有区分声明、探测、授权与最终有效能力。
7. 90% 行覆盖率不能证明长轨迹恢复、幂等和双宿主一致性。

### 2.2 成功标准

- 所有真实 Action/Result 都通过唯一版本化 schema。
- 同一 `action_id` 的重复 Result 不重复推进状态。
- 删除状态投影后，可从事件日志重建等价 EngineState。
- Tick Kernel 只做确定性编排；Stage、持久化、Gate、观测通过明确端口协作。
- Claude Code 与 Codex 对同一黄金轨迹产生等价的 Core 状态与终态 verdict。
- v5.6 checkpoint 在迁移期可读取，不允许静默丢失或原地破坏。

## 3. 设计原则

1. **协议先行**：先修复外部契约，再调整内部结构。
2. **事件为事实，状态为投影**：不可变事件是审计与恢复基础。
3. **渐进替换**：每个 Phase 都能独立发布和回滚，不建立双内核。
4. **宿主能力不等于授权**：只有有效能力可以驱动执行。
5. **副作用显式**：文件、Git、数据库和外部工具通过端口执行。
6. **保持简单**：不引入 LangGraph/OpenHands 运行时；只吸收其成熟设计模式。
7. **设计不可降级**：迁移通过适配层保持兼容，不删除 Gate、Guardrail 或五层验证。

## 4. 目标架构

```text
Claude Code / Codex / Future Host
                │
                ▼
        Host Adapter / Host Profile
                │
                ▼
       Versioned Protocol Envelope
                │
                ▼
             Tick Kernel
      ┌─────────┼──────────┐
      ▼         ▼          ▼
 StageHandler  PolicyPort  EventStore
      │     Gate/Guardrail    │
      └─────────┼─────────────┘
                ▼
         EngineState Projector
                │
                ▼
        Audit / Metrics / Trace
```

### 4.1 分层职责

| 层 | 职责 | 禁止 |
|---|---|---|
| Host Adapter | 事件归一化、能力探测、CLI 解析、宿主执行映射 | 写 Core 业务状态 |
| Protocol | Action/Result/Event/Error 的稳定数据契约 | 宿主专属字段散落顶层 |
| Tick Kernel | 校验输入、应用策略、选择 Handler、提交事件、返回 Action | 直接运行 LLM 或宿主工具 |
| Stage Handler | 单一 Stage 的纯转换或受控决策 | 自行持久化和跨 Stage 偷写 |
| Policy Port | Gate、Guardrail、授权和安全策略 | 修改路由规则 |
| Event Store | 追加、查询、幂等、事务和迁移 | 根据业务含义改写事件 |
| Projector | 从事件生成 EngineState/ProgressTree 等读模型 | 产生新的业务事实 |
| Observability | 审计、指标、trace、调试快照 | 影响状态推进结果 |

## 5. Protocol Envelope v1.1

### 5.1 公共字段

所有跨宿主消息统一包含：

```json
{
  "schema_version": "1.1",
  "message_type": "action",
  "message_id": "uuid",
  "thread_id": "uuid",
  "tick": 3,
  "stage": "developer",
  "causation_id": "previous-message-id",
  "correlation_id": "thread-id",
  "extensions": {}
}
```

约束：

- `message_id` 全局唯一。
- Action 的 `message_id` 同时是 `action_id`。
- Result 必须用 `causation_id` 指向对应 Action。
- `correlation_id` 默认等于 `thread_id`，为未来跨线程协调预留。
- 宿主专属字段只能进入 `extensions.<host>`。
- 公共顶层使用 `unevaluatedProperties: false`；扩展能力通过 `extensions` 开放。

### 5.2 Action 类型

Action discriminator 包含：

- 工作阶段：`gap_scan`、`gap_review`、`research`、`architect`、`developer`、
  `critic`、`component_verifier`、`plate_deep_audit`、`system_verifier`、
  `system_deep_audit`
- 控制类型：`gate`、`skip`
- 终态类型：`done`、`error`

`gate` 必须包含结构化 `gate` 对象；`skip` 必须包含 `reason` 和
`next_transition`；禁止由宿主猜测下一步。

### 5.3 Result 幂等

Event Store 对 `(thread_id, causation_id)` 建立唯一约束：

- 首次合法提交：执行 Tick，记录 ResultAccepted。
- 完全相同的重复提交：返回已生成的 Action，不再次推进。
- 相同 causation、不同 payload：返回 `RESULT_CONFLICT`。
- 未知或已过期 causation：返回 `ACTION_NOT_ACTIVE`。
- schema 版本不支持：返回 `SCHEMA_VERSION_UNSUPPORTED`。

`_last_completed_stage` 降级逻辑在迁移完成后退役，不再以 stage 名代替消息身份。

## 6. 事件化状态

### 6.1 LoopEvent

事件公共结构：

```text
event_id
thread_id
sequence
event_type
causation_id
correlation_id
schema_version
payload_json
created_at
payload_sha256
```

首批事件：

- `LoopInitialized`
- `ActionIssued`
- `ResultAccepted`
- `GateResolved`
- `GuardrailEvaluated`
- `GatesCompleted`
- `StageAdvanced`
- `CheckpointImported`
- `LoopCompleted`
- `LoopFailed`

### 6.2 事务边界

单次 Tick 在一个 SQLite 事务内完成：

1. 校验 Result 和 causation。
2. 追加 ResultAccepted 及后续领域事件。
3. 更新 EngineState 投影。
4. 保存返回 Action 快照。
5. 提交事务。

任何一步失败均回滚，不允许事件已写入但状态未推进。

### 6.3 兼容迁移

- 保留 v5.6 `checkpoints` 表只读访问。
- 首次恢复旧线程时写入 `CheckpointImported`，不修改原记录。
- 新线程只写 events + projections。
- 迁移期 `SQLiteCheckpointStore` 作为兼容 façade，内部委托 EventStore。
- 至少一个完整小版本后，才允许讨论删除旧表读取路径。

## 7. Tick Kernel 与 StageHandler

### 7.1 Tick Kernel

Tick Kernel 固定流程：

```text
load projection
→ validate envelope
→ check idempotency
→ resolve gate or apply result
→ evaluate guardrail
→ run required gates
→ dispatch stage handler
→ append events
→ project state
→ build and persist next action
```

Kernel 不理解具体 Stage 输出字段，只依赖 Handler 契约。

### 7.2 StageHandler 契约

```python
class StageHandler(Protocol):
    stage: StageName

    def apply(
        self,
        state: EngineStateView,
        result: StageResult,
        context: TransitionContext,
    ) -> TransitionDecision: ...
```

`TransitionDecision` 只表达：

- 领域事件列表
- 下一 Stage
- 是否需要 Gate
- 是否终止
- 对下一 Action 的结构化上下文

Handler 不直接写 SQLite、日志或全局 collector。

### 7.3 迁移顺序

1. Gap/Research：依赖少，先验证 Handler 模式。
2. Verification：输出结构明确，适合批量迁移。
3. Architect/Critic：涉及 refine 与 verdict。
4. Developer：最后迁移，保留 Gate、TDD 和 batch 行为。
5. Terminal/Convergence：统一收口终态。

旧 `_after_*` 在对应 Handler 验证完成后删除，禁止长期双实现。

### 7.4 ActionBuilder 无状态化

引入不可变 `ActionBuildContext`，所有依赖通过参数传入。Builder：

- 不保存 `_state`、`_design_doc` 等跨调用字段。
- 相同输入必须产生相同输出（时间戳和 UUID 由 Kernel 注入）。
- 可在多线程和多个 thread 间安全复用。

## 8. Host SPI 2.0

### 8.1 HostProfile

```text
HostProfile
├── declared_capabilities
├── detected_capabilities
├── authorized_capabilities
└── effective_capabilities
```

`effective = declared ∩ detected ∩ authorized`。

- declared：适配器理论支持。
- detected：当前会话实际可用工具和模式。
- authorized：用户对副作用的当前授权。
- effective：Action 执行时唯一允许使用的能力。

### 8.2 CapabilityRequirement

Action 可声明：

```json
{
  "capability_requirements": {
    "subagents": true,
    "parallel_subagents": false,
    "interactive_questions": false,
    "git_operations": []
  }
}
```

宿主不满足时返回结构化 `HOST_CAPABILITY_UNAVAILABLE`，不得伪造或隐式降级。

### 8.3 接入新宿主

新宿主必须提供：

1. `detect()`
2. `normalize_event()`
3. `resolve_cli()`
4. `probe_capabilities()`
5. `map_action()`
6. `collect_usage()`

通过 Host SPI 合同测试后才能列为“已支持”。仅存在 enum 或 hook 文件不等于支持。

## 9. 验证战略

### 9.1 测试金字塔

| 层 | 目标 |
|---|---|
| Schema contract | 所有真实 Action/Result 分支均符合 schema |
| Handler unit | 单 Stage 输入到 TransitionDecision |
| Kernel integration | 幂等、事务、Gate、Guardrail 和事件顺序 |
| Replay | 事件重建状态与原投影等价 |
| Fault injection | 崩溃、超时、重复、乱序、损坏事件 |
| Golden trajectory | 固定需求从 init 到终态的完整轨迹 |
| Cross-host | Claude/Codex 产生等价 Core 事件和终态 |

### 9.2 黄金轨迹

至少覆盖：

1. 普通 architect → developer → critic → done。
2. critic MAJOR → developer 重做。
3. Gate 暂停、审查、继续和终止。
4. Result 重复提交与冲突提交。
5. 进程在事件提交前后崩溃。
6. v5.6 checkpoint 导入。
7. verifier negative recheck。
8. plan_refine 达到分源与全局上限。
9. Host capability 不足。
10. Claude/Codex 同轨迹一致性。

### 9.3 发布门禁

- 全量测试不得低于当前基线。
- 覆盖率不得低于 90%。
- Schema、事件 replay、双宿主 contract 为独立 CI job。
- 不把 archive smoke 冒充真实产品安装。
- 性能基线：纯编排 P95 不高于 v5.6 基线的 120%。

## 11. 风险与控制

| 风险 | 控制 |
|---|---|
| 事件化导致迁移范围过大 | Phase 52 先稳定协议；Phase 53 保留兼容 façade |
| 双实现长期存在 | 每个 Handler 任务都包含删除旧 `_after_*` 的完成条件 |
| Schema 严格化破坏宿主扩展 | 保留显式 `extensions`，禁止顶层任意字段 |
| 事件与投影不一致 | 单事务写入；replay equality 测试 |
| 多 Agent 成本膨胀 | Core 不增加 Agent 数；由 Action 声明最小能力需求 |
| 过度抽象 | 只为现有 Claude/Codex 和已知消息类型设计，不预建云端队列 |

## 12. 明确不做

- 不在 Core 中调用 LLM。
- 不恢复 StandaloneDriver。
- 不引入 LangGraph、OpenHands 或 SWE-ReX 运行时依赖。
- 不实现多租户服务端、任务队列或远程 Worker。
- 不删除 Gate、Guardrail、五层验证或 Init-Loop 契约。
- 不在本轮改变用户授权和 Git 安全边界。
- 不以代码行数作为唯一重构成功指标。
