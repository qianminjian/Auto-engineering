# v5.8 Effective Design Authority Projection

> 状态：已批准实施｜日期：2026-08-28｜追踪：T554-T557

## 1. 要解决的主问题

Loop 的产品目标不是“记住用户点过批准”，而是：用户只批准一次，随后任何新会话、新 Agent、恢复进程都从同一确定性状态看到该决策，并继续收敛到 Developer 和 `TERMINAL`。

真跑暴露的根因是设计权威读写分裂：

1. Gate 批准被排入待提交的 `GateResolved` 事件。
2. 同一 Tick 在事件提交前构建下一 Architect Action。
3. ActionBuilder 独立重读项目静态 ledger，不读取当前 Tick 的批准投影。
4. 文本 feedback 说“已批准”，结构化 ledger 却为空；Agent 按权威规则必须再次请求批准。

这是 Tick 一致性与投影边界缺陷，不是 Prompt 措辞或 ledger 文件格式问题。

## 2. 方案与决策

### 方案 A：批准后回写静态 ledger

优点是改动小。缺点是引入 EventStore 与文件双写，中断时可能只成功一边，并违反 D9。不采用。

### 方案 B：内核统一有效设计权威投影

由 Core 生成 `EffectiveDesignAuthorityProjection`，合并静态设计决策与 EventStore 中已批准的设计变更。Tick Kernel 用“上一投影 + 当前待提交事件”计算下一投影，再编译 Action。

采用方案 B。静态 ledger 仍是设计资产，但不再充当运行态批准的事实源。

## 3. 单一权威模型

```text
Static Design Ledger -----\
                           +--> EffectiveDesignAuthorityProjection --> Action
Committed Domain Events --/
Current Tick Events ------/
```

投影的最小契约：

```json
{
  "schema_version": "1.0",
  "source_ref": "design/example.md",
  "source_sha256": "...",
  "semantic_enforcement": "partial",
  "decisions": [],
  "approved_changes": [
    {
      "decision_id": "change-...",
      "proposed_change_sha256": "...",
      "approval_id": "result-...",
      "authority_scope_key": "sha256(source + source_ref + canonical refs)",
      "source_ref": "gap-...",
      "status": "approved"
    }
  ]
}
```

`authority_scope_key` 由 `source + source_ref + 排序去重后的 affected_design_refs` 生成，是已处置设计问题的稳定身份；`decision_id + proposed_change_sha256` 保留当次原文审计。Agent 仅改写摘要或调整 refs 顺序不得重新触发 Gate；实质新问题必须使用新 `source_ref` 或明确的新影响范围。

## 4. Tick 事务顺序

正确顺序必须是：

1. 校验 active Gate Result 的因果身份。
2. 生成 `GateResolved` 领域事件。
3. 用上一状态和当前 Tick 事件计算 candidate projection。
4. 从 candidate projection 编译下一 Architect Action。
5. 在同一 EventStore Tick 事务中提交 Result、Event、Projection 和 Action。
6. 失败时全部回滚；恢复和重放必须生成字节等价的有效权威投影。

旧事件缺少 `authority_scope_key` 时，投影器必须从同一 EventStore 中先前的 `ActionIssued.gate.change` 回算；无法回算时才保留原文摘要精确匹配，不改写历史事件。

ActionBuilder 只消费调用方传入的投影，禁止自行从项目目录重读 ledger。文本 feedback 只用于人类可读说明，不得承载机器权威。

## 5. 收敛不变量

1. **唯一事实源**：运行态批准只由事件及其投影证明。
2. **因果可见**：产生批准的 Tick 所发出的下一 Action 必须已看到批准。
3. **新 Agent 独立性**：不得依赖聊天历史、feedback 或旧 Agent 记忆。
4. **不重复请求**：已批准的相同稳定来源范围再次提交变更请求时 fail-closed，并要求生成可执行计划。
5. **内容绑定**：设计文档内容发生变化时，不能静默复用旧批准。
6. **重放等价**：进程重启、会话清空或宿主更换不改变投影结果。

## 6. 验收架构

发布门禁不再以单元测试数量代替产品闭环，必须分层证明：

| 层级 | 必须证明 |
|---|---|
| L1 投影 | 批准事件和 candidate projection 的确定性、内容绑定与重放 |
| L2 Tick 轨迹 | 同 Tick 的下一 Action 已含 binding 批准，并阻止重复请求 |
| L3 隔离 Host | Research→Gate→Approval→新 Architect→batch plan→Developer |
| L4 真实宿主 | Codex 和 Claude Code 安装制品均在新会话中完成同一轨迹 |

L1/L2 通过不得宣称产品完成。L3/L4 必须检查下一 Architect 的实际结构化输入和最终阶段，不能只检查“事件存在”或“Action 类型为 architect”。

## 7. 非目标

- 不通过增加更多提示词规则解决状态问题。
- 不要求主会话记住批准结果。
- 不引入新的用户管理命令。
- 不为了让测试变绿而降级 partial authority 的保守约束。
