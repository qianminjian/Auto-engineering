# Auto-Engineering v5.7 协议内核实施计划

> **执行者要求：** 实施时使用 `executing-plans`；功能与缺陷任务使用
> `test-driven-development`；声明阶段完成前使用
> `verification-before-completion`。

**目标：** 在保持 v5.6 可用与可恢复的前提下，将 Core 渐进重构为版本化协议、
事件事实源、轻量 Tick Kernel、可插拔 StageHandler 和可探测 Host SPI。

**架构：** 先修复外部协议闭包，再建立 append-only EventStore 与状态投影；
随后逐组迁移 StageHandler，最后升级宿主能力协商和跨宿主黄金轨迹。每个 Phase
独立验收，兼容 façade 在迁移期保留，不建立第二套并行内核。

**技术栈：** Python 3.12+、JSON Schema 2020-12、SQLite、pytest、Ruff、mypy。

> Phase 52-56 已完成。真实长会话运行暴露的 Session、PlanPatch、验证可信度和成本
> 问题不回填进已完成任务，统一由
> `design/v5.8-Session-Decoupling-PLAN.md` Phase 64-67 实施。

**执行约束：** 测试串行运行；单文件使用
`uv run pytest <file> -v --no-cov --timeout=60`；全量测试只在阶段收口执行。
未经用户另行授权，不提交、不推送、不发布。

## Phase 52：Protocol Envelope v1.1（P0）

### T242：锁定现有契约盲区

**文件：**
- 修改：`tests/test_action_result_contract.py`
- 修改：`tests/test_actions.py`
- 读取：`auto_engineering/loop/action.schema.json`
- 读取：`auto_engineering/loop/stage-result.schema.json`

**EARS：** While Core 会发出控制 Action, when schema 校验 `gate` 或 `skip`,
the validator shall 接受真实 payload 且拒绝未声明字段。

**步骤：**
1. 增加 `gate`、`skip`、未知 action type、额外顶层字段的契约测试。
2. 增加 Result 缺少 `causation_id`、版本不支持和错误 message type 的测试。
3. 运行两个测试文件，确认新测试以契约缺失原因失败，并记录 RED 证据。

### T243：实现公共 Envelope 与闭合 schema

**文件：**
- 新增：`auto_engineering/loop/protocol.py`
- 修改：`auto_engineering/loop/action.schema.json`
- 修改：`auto_engineering/loop/stage-result.schema.json`
- 修改：`auto_engineering/loop/actions.py`
- 修改：`tests/test_action_result_contract.py`

**EARS：** While 任意宿主交换 Action/Result, when 消息进入 Core, the protocol
shall 校验 `schema_version`、消息身份、因果关系和扩展边界。

**步骤：**
1. 定义 `ProtocolEnvelope`、`ActionEnvelope`、`ResultEnvelope` 和稳定错误码。
2. 将 `gate`、`skip`、`done`、`error` 纳入 discriminator。
3. 顶层设为严格字段，宿主数据只允许进入 `extensions.<host>`。
4. 运行 T242 测试转 GREEN，再运行 `tests/test_cli_dev_loop_tick.py` 防回归。

### T244：实现 Action/Result 因果与幂等语义

**文件：**
- 修改：`auto_engineering/loop/tick_orchestrator.py`
- 修改：`auto_engineering/loop/checkpoint/store.py`
- 新增：`tests/test_result_idempotency.py`

**EARS：** While 一个 Action 已生成, when 相同 Result 重复提交, the Core shall
返回同一后继 Action 且状态只推进一次。

**步骤：**
1. 先覆盖首次提交、完全重复、payload 冲突、未知和过期 causation 的 RED 测试。
2. 保存 active action 与结果摘要，按 `(thread_id, causation_id)` 判定幂等。
3. 返回 `RESULT_CONFLICT`、`ACTION_NOT_ACTIVE` 等稳定错误。
4. 运行新测试和 `tests/test_tick_orchestrator.py`。

### T245：提供 v1.0 兼容入口

**文件：**
- 新增：`auto_engineering/loop/protocol_compat.py`
- 修改：`auto_engineering/cli.py`
- 新增：`tests/test_protocol_compat.py`

**EARS：** While v5.6 客户端提交旧 Result, when 兼容入口可唯一推断对应 Action,
the adapter shall 转换为 v1.1；歧义时 shall fail closed。

**步骤：**
1. 为无 envelope 的旧 payload 写兼容和歧义 RED 测试。
2. 只在存在唯一 active action 时补齐 envelope，并发出结构化弃用告警。
3. 不允许以 stage 名覆盖不匹配的 action identity。
4. 运行兼容测试、CLI tick 测试和告警契约测试。
