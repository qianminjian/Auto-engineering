# v5.8 Host Runtime 收敛设计分析附件

> 日期：2026-08-16｜适用阶段：Phase 83｜性质：永久分析记录
> 关联设计：`v5.8-Host-Runtime-Convergence-Design.md`
> 关联计划：`v5.8-Host-Runtime-Convergence-PLAN.md`

## 1. 分析结论

历次真跑反复出现底层故障，不是某个 Prompt、批次或 Voice Clone 业务实现有问题，而是
Loop 工程曾把“协议组件存在”和“安装后的宿主产品链路闭合”混为一谈。单元测试分别证明
Action、Result、Event、Worker proof 可以工作，却没有证明真实 Skill、Command、Hook、
原生 Worker 和 Core 在同一次启动中形成连续、不可绕过的因果链。

本次收敛坚持原始定位：宿主负责推理和工具执行，Auto-Engineering 负责协议、状态、验证、
安全和审计。Core 继续保持确定性单 Tick，不引入后台 daemon、用户可见 supervisor 或额外
continue 命令；自动续跑由插件产品层驱动，执行事实由 EventStore 和原子证据事务固化。

## 2. 为什么过去会“越改越错”

### 2.1 验收层级错位

过去的 archive smoke、Fake Host 和组件测试验证了“包能运行”“类能调用”，却被错误地用来
推断真实 Claude Code/Codex 会持续驱动。真实宿主实际消费的是 Skill/Command 的自然语言
协议和原生子代理结果；这条路径未进入同一验收轨迹，导致测试绿而真跑立即停顿。

### 2.2 状态存在两个写入者

旧路径同时由 TransitionEffectExecutor 修改进程内游标、由事件 Reducer 修改投影。Plan
refine 又从数组下标恢复活动批次，使已完成事实可能被重新激活，最终出现 10/14 被显示为
14/10 或 140%。问题本质不是百分比公式，而是完成事实、游标和总量没有唯一所有者。

### 2.3 Worker 证明由 Coordinator 手工拼装

Core 发出 challenge 和模板后，宿主仍需手工创建 receipt、attestation 和 total proof。
任何字段遗漏都会被 Core 拒绝；宿主为了继续又重复 spawn 或反复修 JSON，扩大上下文和
token。证明内容虽“严格”，生产生成方式却不是确定性事务。

### 2.4 设计权威只在文档层声明

partial ledger 被理解成“允许 Agent 补充设计”，Research/Critic 的建议可能直接进入 binding
计划。批准字段曾可由任意字符串伪造，合法批准又没有稳定 EventStore 投影，导致设计约束
既可能被绕过，也可能永久无法通过。

### 2.5 会话状态与工程状态混杂

宿主回复结束、聊天 `/clear`、checkpoint 恢复和工程进度曾被混为同一状态。实际上聊天历史
不是事实源；只要项目 `.ae-state` 仍保存活动 thread，显式设计文档与旧执行状态就必须由
Core 协调，而不能由聊天清理动作隐式决定。

## 3. 统一目标架构

```text
User invocation
  -> installed Skill / Command
  -> HostRuntimeDriver + HostRunLease
  -> Core Tick emits Action + ExecutionControl + evidence template
  -> native Worker or inline Developer or explicit User Gate
  -> HostExecutionAssembler atomically finalizes evidence and Result
  -> Core validates Result and appends domain events
  -> Reducers rebuild projections and emit next Action
  -> StopGuard blocks accidental yield while disposition is CONTINUE
```

边界如下：

1. Core 不调用 LLM、不管理后台会话，也不猜测宿主能力。
2. Host Runtime 不修改业务状态，只履行当前 Action 的执行义务。
3. Worker 只返回原生 outcome，不写共享证明文件，也不驱动 Loop。
4. Assembler 是严格合同下证明与完整 Result 的唯一生成入口。
5. EventStore 是完成事实、批准事实、refine 和指标的唯一持久化来源。
6. 用户只有在 `WAIT_USER` 的真实 Gate 才需要介入。

## 5. 关键不变量

1. `CONTINUE` Action 未完成时宿主不得向用户交回控制。
2. active Action、RunLease、Result、receipt 和 attestation 必须绑定同一 message identity。
3. `spawn.count == len(invocations) == len(worker outcomes)`。
4. Worker 成功 outcome 已落盘时，恢复只能 finalize，不能重新 spawn。
5. `done_tasks <= total_tasks` 且 completion 永不超过 100%。
6. Batch/Component/Plate 游标只由对应领域事件推进一次。
7. advisory 信息不能变成 binding obligation，除非存在可重放的用户批准事件。
8. usage 未知必须报告 incomplete，不能以零掩盖。
9. archive smoke、测试数量和自报 JSON 都不能替代真实产品 L3/L4。
10. Release 安装与运行来源不得回指开发工作区。

## 7. 剩余工作与发布纪律

1. 从同一内容寻址 Release 安装 Claude Code/Codex，执行 L3 并保存受校验 artifact。
2. L3 双宿主通过后执行 Voice Clone L4；任一人工续跑、手工 proof 修复、投影漂移或未经批准
   的设计变化均判失败。
3. L3/L4 证据缺失时保持 `not_run`，不得生成或发布新 RC。

## 8. 防止再次退化的评审准则

后续每个改动必须回答：它修改的是 Core 确定性规则、Host 产品执行、状态事实、证据生成，
还是产品验收？跨层修改必须有生产轨迹测试，不能只给目标类增加单测。任何为了让当前真跑
继续而新增的手工 JSON、自由文本恢复、宿主特例或第二状态写入者，都与本设计冲突，应在
代码评审阶段拒绝。

## 9. 2026-08-16 首轮 Codex L3 新证据

同一内容寻址 Build `5.8.0-rc.5+sha256.215aa36c5561f567` 安装后，在全新 Canary 项目中
成功完成 doctor、配置初始化和 Loop init，但暴露出两项产品链路缺口：

1. Codex Skill 首次调用裸 `ae-run` 返回 exit 127，随后由宿主搜索插件缓存路径才恢复。
   这证明发布包位置无关不等于宿主入口可发现；Skill/Command 必须从自身安装位置确定性
   解析 bundled runner，不能依赖 PATH 或让 Agent 搜索文件系统。
2. 首个 `gap_scan` Action 不含 spawn。宿主按业务格式生成 `gaps/scanned_sections/has_blocking`
   后手工提交，Core 以 `ACTION_NOT_ACTIVE` 拒绝；宿主随后读取协议并补写 message identity
   才能推进。现有 `--finalize-result` 只接受 Worker outcomes，因此严格 Result 的唯一生成
   入口没有覆盖非 spawn Action。

第二项是架构缺口而非 Prompt 文案问题：Result identity、causation、thread、tick、stage 和
correlation 都属于 Core 掌握的 active Action 事实，不应由宿主推理或复制。T470 将扩展同一
`HostExecutionAssembler`：非 spawn Action 只需 coordinator payload；严格 spawn Action 仍需
原生 outcomes。两类 Action 都由同一 finalization 命令生成完整 Result，再进入 validate/tick。
该设计同时消除手工协议漂移和为修复 JSON 重读上下文的 token 放大。

同一次旧 Build 轨迹随后在 Architect Gate 暴露第三个边界错位：顶层 Action 虽有
`valid_plate_keys`，隔离 Worker 实际只接收内容寻址的编译 Prompt，而该字段不在 Architect
Prompt Contract 中。Worker明确拒绝虚构并提交空 `plate_keys`，Core 随即以
`ARCHITECT_PLAN_INVALID` 终止。修复原则不是放宽 Gate，而是让 Gate 的合法输入域进入同一
Worker 执行上下文：Action 顶层机器字段与 Prompt Context 必须携带完全相同的稳定 key 集合。
这项不变量登记为 T471，并以真实 Prompt 内容回归测试约束。

T470 第一版仍把完整 Result 只输出到 stdout，并要求宿主“保存为文件”。真实 Codex 首次
继续使用原 coordinator payload 执行 validate，触发一次 `ACTION_NOT_ACTIVE` 后才人工复制
stdout。这说明“生成内容确定性”仍不等于“提交事务确定性”。最终合同增加
`--output-result`：Finalizer 在项目边界内原子写入完整 Result，宿主直接把该文件交给
validate/tick；越出项目根的输出路径 fail-closed。由此 payload → Envelope → 文件 → Tick
不再包含 LLM 复制步骤。

同一轨迹进入 Architect 后又证明协议存在“双写”：Skill 要求 Worker/Coordinator 不得写 proof，
但 v1.1 Action 的 `instruction` 仍沿用旧版，要求覆盖 total proof、worker receipt，并在业务
payload 中手工加入 `spawned/spawn_proof_token`。宿主遵循更靠近 Action 的旧指令，导致
`HOST_OUTCOME_INPUT_INVALID` 和 proof 被提前修改。T472 不放宽 Assembler，而是从生产
Action 删除旧证明算法：当前合同只允许消费 `spawn.invocations[]`、记录精确
`{"outcomes":[...]}` 原生事实，并调用 Finalizer；receipt、attestation、proof 与 Result
继续由 Assembler 独占写入。旧合同兼容只能在明确旧 Runtime Vector 的迁移分支存在。

第四轮轨迹进入 inline Developer 后，Action `expected_format` 仍要求 `stage=developer`，而
Finalizer 正确拒绝 coordinator 覆盖 `stage`，导致 `COORDINATOR_IDENTITY_OVERRIDE` 后宿主
自行删字段重试。T473 将同一规则提升到 ActionBuilder：任何面向 Coordinator 的
expected_format 都自动剔除 schema/message/causation/thread/tick/stage/correlation、spawn proof
等 Core-owned 字段；Worker业务格式可保留角色输出需求，但最终 Envelope 身份只由 active
Action 决定。这样 Core 不再同时要求宿主“写入”和“禁止写入”同一字段。

第五轮轨迹已经完成 Architect、Developer、Critic、Component Verifier 和全部自动 Gate，却在
System Deep Audit 后错误进入 PLAN_REFINE。唯一 P1 的描述和 suggested_fix 同时明确“该建议
超出当前独立纯函数设计范围、当前设计无需修改”；Core 仍只按 severity 字符串机械阻断，证明
审计结果缺少设计权威分类。随后 Architect Action 因已完成 Worker 句柄未及时回收而耗尽宿主
容量，Host 在 `CONTINUE/yield_allowed=false` 下仍退出。T474-T475 将两项问题作为同一产品
闭环修复：P0/P1 必须声明 `binding_violation` 或 `objective_defect` 才可触发 refine，advisory/
out_of_scope 只保留审计证据；每个阶段的原生 Worker 输出落入 outcome 后必须立即回收句柄，
不得把已完成 Worker 的生命周期泄漏到下一 Action。两项均需真实 L3 复验，不能以 Prompt
单测或 Fake Host 代替。

新 Build 的有效 L3 随后证明 T473 只关闭了 Action 表层：Critic Action 的
`expected_format` 已无 `stage`，但 PromptCompiler 在过滤之前编译 Worker 输出契约，仍向
隔离 Worker 明示 `stage=critic`。Worker 合法遵循 Prompt，Coordinator 照搬业务 payload 后被
Assembler 以 `COORDINATOR_IDENTITY_OVERRIDE` 拒绝并手工删字段重试。T476 要求 Core-owned
字段在 PromptCompiler 输入边界一次性剔除，使 Worker Prompt、Coordinator expected_format
和 Finalizer 共享同一业务字段集合；不得依赖宿主理解两份矛盾合同后自行纠偏。

下一轮 L3 在 Component Verifier 暴露跨 Action 文件复用污染：宿主已写入新的 Worker outcome，
但 finalize 前 `coordinator-result.json` 仍是上一轮 Critic 业务字段。Assembler 只防身份覆盖，
未按 active Action 的 `expected_format` 拒绝陈旧业务字段，因而先提交了错误 journal；宿主纠正
payload 后才得到 `OUTCOME_JOURNAL_CONFLICT`。journal 已按 action message 隔离，无需改名。
T477 的正确修复是在任何 journal/receipt/proof 写入前，对 Coordinator payload 做 active
Action 字段白名单校验；跨阶段字段一次性全部返回，且不得产生 prepared journal。

Build `5.8.0-rc.5+sha256.2fedd67a7eef71ef` 的 Codex L3 已于 2026-08-16 真实到达
`TERMINAL / GOAL_ACHIEVED`。单次宿主启动完成 11 Tick：首次实现后系统审计正确发现 default
step 成功路径未测试，5 个审计 Worker 全部回收，Architect refine 成功继续，第二轮开发、
Critic、Component Verifier 与 System Deep Audit 后终止。RunLease 最终为
`continuation_required=false/disposition=TERMINAL/yield_allowed=true`；过程中无人工续跑、proof

这条证据关闭 Codex 侧 T470-T477，但 Claude L3 与 Voice Clone L4 仍为发布阻断项。

同 Build 的首次 Claude L3 在 Gap Scan 合法发现原 Canary 设计未明确返回计算语义、精确 int
子类边界和 TypeError 消息契约，进入 `WAIT_USER`；Codex 对同文档未报告 gap。该结果不能
归因于 Host Driver，也不能用自动采纳建议绕过。它证明验收夹具本身仍允许合理分歧，无法
作为跨宿主等价标准。T478 将 L3 Canary 固化为项目内黄金资产，明确 `current + step`、
exact built-in int、校验顺序及非契约错误消息；两宿主必须消费同一字节摘要后再比较轨迹。

同摘要 Claude 轨迹虽到达 TERMINAL，却在 finalize 前因宿主工具把当前目录切换到
`.ae-state/effects/prompt` 而出现 `PROJECT_THREAD_NOT_ACTIVE`，随后由宿主返回项目根目录重试。
这不是可接受的“自愈”：它说明内部协议仍把易变 shell `cwd` 当作隐藏状态。T479 将绝对
`project_root` 固化为每个 Action 的机器字段，Finalizer/Validator/Tick 的相对 artifact 路径
统一相对该根目录解析，Skill 与 Command 要求每条内部命令显式传递该值。宿主目录漂移因此
不再改变 thread、EventStore 或 outcome 的寻址，也不需要任何重试策略。

`build_id` 为 `unknown`。Action 已在 `extensions.ae.runtime_revision.engine_build_id` 携带真实
Build，Lease 却仍读取退役的 `runtime_vector`/`extensions.ae.runtime` 路径。T480 统一从当前
Runtime Revision 投影 Build Identity；未知 Build 不得作为双宿主同制品验收证据。

T480 Build 的新鲜 Claude Gap Scan 又发现黄金设计未规定 `__init__.py` 和包导入面，进入
合法 `WAIT_USER`。T481 继续收紧验收输入：规定 regular-package src layout、空

验收不能靠自动替用户选择 Fill 来掩盖设计缺口；只有新摘要的两宿主轨迹可比较。

重装同 Build 时安装器拒绝已暂存 Release：Claude 运行期间在插件根生成了 `.venv`。根因是
T479 只绑定 Loop 内部命令，业务 `uv run` 仍可能继承插件 cwd；旧 `ae-run` 又会优先执行
插件 `.venv/bin/ae`，使污染进一步成为运行时选择。T482 将所有编辑/测试/lint/type-check/
build/Worker 启动固定到 `action.project_root`，并删除启动器的 `.venv` 分支；插件只允许使用
专属 `.ae-runtime`。安装器继续把 Release 内 `.venv` 判为篡改，不以忽略符号链接掩盖污染。

新 Build Claude 轨迹在 Component Verifier 暴露 receipt 尺寸口径不一致：压缩器按 Worker
payload 是否小于 4096 决定 inline，Assembler 随后追加 handle，而验证器按完整 envelope
是否小于 4096 校验，形成约 3800–4096 字节的确定性失败窗口。宿主删除 journal 并缩短
payload 才继续，违反原子幂等目标。T483 改为在写 journal/proof 前用包含身份、模型、effort、
native handle 的完整 receipt 计算预算；超限直接走 ArtifactRef，验证器共享同一 4096 上限。

T483 Build 的新鲜 Gap Scan 发现 L3 手工创建的 `pyproject.toml` 未声明 build backend，设计却
要求 build 通过，因而合法进入 `WAIT_USER`。T484 将工程基线也纳入黄金资产：设计明确
`hatchling.build`，项目夹具固定 `[build-system]`、wheel package 路径和版本范围。以后 L3
不得临时手写不同 pyproject；同宿主比较输入是“设计摘要 + 工程基线摘要”，不是单一 Markdown。

Prompt 已要求业务 cwd 后，Claude 仍在 Release 根创建 `.venv`，证明宿主指令不是不可变制品
边界。T485 将防线下沉到安装层：安装与 doctor 创建专属 `.ae-runtime` 后，Release/插件缓存
除该子树外全部 seal 为只读；`ae-run` 设置 `PYTHONDONTWRITEBYTECODE`，继续只使用
`.ae-runtime`。后续宿主即使错误执行 `uv run` 也不能在制品根创建 `.venv`，安装复验仍会
拒绝任何专属运行时之外的符号链接。

物理封存 Build 的 Gap Scan 又发现设计只写 lint/type-check/build 通过，未绑定具体命令；手工
`ae.toml` 虽有命令，但不属于 binding design。T486 将四条项目根命令逐字写入设计，并把
`ae.toml` 作为第三个黄金夹具（项目类型纠正为 library）。L3 输入身份由 design、pyproject、

### 真跑发现：Worker 超时被错误送入成功终结器（T517）

Architect 修复 Worker 在三次显式等待后仍未完成。宿主如实记录了原生 handle、`errored` 状态和超时摘要，却继续拼装空的 coordinator plan 并调用只接受 completed outcome 的成功终结器，最终得到 `WORKER_NOT_COMPLETED` 后停止。根因不是等待时间不足，而是 HostExecutionAssembler 缺少失败事务：Core 已识别 `HOST_WORKER_TIMEOUT`，Skill 却使用漂移的 `HOST_AGENT_TIMEOUT`，Assembler 又无法从原生失败事实生成该协议 Result。

修复必须收敛为同一条路径：Assembler 验证失败 outcome 与 active Action 的 Worker 集合和原生 handle，忽略任何业务载荷，生成确定性的 `spawned=false/HOST_WORKER_TIMEOUT` Result，并将 outcome journal 标为可重试的 `worker_failed`；不得写成功 proof、receipt 或 attestation。Core 把它投影为不替换 active Action 的 `WAIT_RESOURCE`，且不计入 Architect 业务计划修复次数。失败 journal 不得触发 T512 的成功恢复锁；下一次 init 必须重新投影原 active Action 并允许合法 Worker 重试。这样重试仍由 Core 决定，宿主不伪造完成，也不要求用户重启。

最终 Build 的同一 checkpoint 证明了上述续接，但也揭示“有界”的第二层含义：宿主会自然写出 `status=timeout`，而初版仅接受 `timed_out`；更重要的是，每个 Worker 的三次等待虽有界，Core 对重新创建 Worker 的次数没有上限，第一次 `WAIT_RESOURCE` 后会再次启动 Worker，若服务持续断流便重新制造无限输入成本。T518 因此把两种超时枚举统一归一化，并由 Assembler journal 生成不可由自然语言驱动的 attempt；Core 只允许一次自动重启，第二次超时稳定终止资源重试。该计数与 Architect 业务修复预算分离。
