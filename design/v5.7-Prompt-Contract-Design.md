# v5.7 Prompt Contract 兼容式重构设计

> 状态：已批准，实施中｜日期：2026-07-28｜阶段：Phase 60
> v5.8 有界上下文、ResumeCapsule 和 ArtifactRef 扩展见
> `design/v5.8-Session-Decoupling-Design.md`。

## 1. 问题与目标

当前提示词由角色 Markdown、Action `expected_format`、`RESULT_SCHEMA` 和
StageHandler 分别维护。实际运行中已出现上下文只存在于 Action、未进入工作 Agent
提示词，角色输出与 Result 校验值域冲突，以及多 Agent 共用一份执行证明等问题。

本阶段在不改变 Action/Result v1.1 核心语义的前提下，引入内部 Prompt Contract：

1. 每个执行角色获得完成任务所需的真实上下文、角色和输出约束。
2. Team Lead、Worker Agent 和 Inline Executor 的职责可区分、可验证。
3. 多 Agent 的每个 Worker 独立获得上下文，并留下独立完成回执。
4. 提示词渲染、结果校验和 Handler 消费字段来自可核对的统一契约。
5. 日志区分“内核渲染”“宿主投递声明”“结果消费”，不把渲染日志冒充实际投递。

## 2. 兼容边界

### 2.1 保持不变

- Action/Result `schema_version` 保持 `1.1`。
- 现有 stage、`subagent_prompt`、`spawn.agents[]`、`expected_format` 和 Result
  核心字段继续可用。
- Claude Code、Codex 继续通过宿主 Skill 驱动 `scripts/ae-run`。
- 当前合法的旧 Result 在迁移期继续接受；新增完整性要求先产生结构化警告。
- Core 不调用 LLM，不复制宿主 Agent Runtime。

### 2.2 允许的兼容扩展

- Prompt 契约版本、渲染哈希和 Worker receipt 摘要写入既有 `extensions`。
- `spawn.agents[]` 可增加 `role`、`prompt_hash`、`receipt_token` 等可选字段。
- 总 `spawn_proof_token` 继续保留；它表示 Coordinator 对全部 Worker receipt
  的汇总确认，不再由多个 Worker 并发覆盖同一文件。

## 3. 内部模型

新增不可变内部模型 `StagePromptContract`，不作为新的外部协议：

```text
StagePromptContract
├── stage
├── execution_mode: inline | single_worker | multi_worker
├── role_definition
├── required_context
├── worker_roles
├── worker_output_contract
├── final_result_contract
└── compatibility_policy
```

`PromptCompiler` 接收 Contract 和一次 Action 上下文，输出：

```text
CompiledPromptBundle
├── coordinator_prompt
├── worker_prompts[]
├── expected_format
├── prompt_hashes
└── contract_warnings[]
```

角色 Markdown 继续承载稳定方法论与检查清单；动态 requirement、feedback、文件、
设计项和验证证据由 Compiler 注入。输出字段和值域不得继续在多个 Markdown 中手写
相互矛盾的副本。

## 4. 角色与上下文契约

| 阶段 | 执行角色 | 必需上下文 |
|---|---|---|
| gap_scan | Inline Executor | design_doc_path、project_root、requirement |
| research | Inline Executor | gap、knowledge_sources、requirement |
| architect | Worker Architect | requirement、design_doc_path；refine 时必须有 feedback |
| developer | Inline Developer | batch_id、component、tasks、requirement、feedback、toolchain |
| critic | Worker Critic | requirement、files_changed、test_results、设计范围 |
| component_verifier | Worker Verifier | component、design_section、design_spec、implementation_files |
| plate_deep_audit | Coordinator + 3 Workers | plate、components、各 Worker 审计维度 |
| system_verifier | Worker Verifier | design_doc_path、file_list、组件 coverage 摘要 |
| system_deep_audit | Coordinator + 5 Workers | coverage_map、缺失/偏离项、项目审计范围、各 Worker 维度 |

必需上下文缺失时，Compiler 返回 `PROMPT_CONTEXT_MISSING`，不得让 Agent 自行猜测。
兼容期内仅对旧 checkpoint 无法恢复的非关键上下文产生 warning。

## 5. 多 Agent 协议

1. 多 Agent 模板必须精确包含一个 Coordinator 区和配置数量相等的 Worker 区。
2. Worker prompt 必须包含唯一角色、任务范围、动态上下文和 Worker 输出结构。
3. Worker 不负责最终 Result 合并；Coordinator 校验 Worker 数量后合并去重。
4. 模板段数、角色数或 Agent 数不一致时 fail closed，禁止复制完整提示词兜底。
5. 每个 Worker 使用独立 receipt token 和文件；Coordinator 收齐后完成总 proof。
6. receipt 只证明执行完成和输出哈希，不记录思维链。

## 6. 输出契约与兼容策略

`final_result_contract` 是字段、类型和值域的权威描述，并被用于渲染
`expected_format` 和检查 `RESULT_SCHEMA` 一致性。

第一阶段不骤然提升旧可选字段为硬必填：

- 缺少已被 Handler 消费的字段时记录 `contract_warning`。
- 修正 Verifier 的 `UNCLEAR` 冲突：Prompt 统一输出
  `IMPLEMENTED | MISSING | DIVERGED`；设计模糊作为 note/findings 表达。
- `strengths`、`recheck_log`、`cross_component_issues` 等字段明确区分为
  业务结果、审计附加信息或删除候选；未经兼容评估不直接删除。
- Developer 的测试证据必须提供；Git commit 仅在宿主已获授权时执行，
  `commit_hash` 不再作为无条件完成前提。

## 7. 日志与审计

Prompt 日志是诊断资产，不是 LLM 投递事实。日志类型：

| 类型 | 内容 |
|---|---|
| rendered | Compiler 生成的 Coordinator/Worker 提示词、哈希和契约版本 |
| dispatch | 宿主声明的目标角色、Agent index 和投递状态 |
| receipt | Worker 返回状态、输出哈希和验证结果 |
| consumption | Result 中已消费、缺失、兼容接受和忽略的字段 |

文件名包含 `thread_id/tick/stage/message_id/audience/index/hash`，采用不可覆盖写入。
日志不得记录思维链；用户上下文按现有 PII 策略脱敏。当前 `_scratch/prompt-log`
继续作为默认目录，但标题改为“内核渲染提示词”。

v5.8 进一步区分 rendered prompt、宿主 delivery/receipt 和 usage ledger，三者不得
互相冒充。大型 Worker 与审计正文改用不可变 `ArtifactRef`，主会话只交付有界摘要
和引用。“上下文完整”表示必需字段不丢失，不表示拼接完整历史；Stage Context
Selector 只选择 active task、直接依赖、最新反馈和必要证据。

## 8. 失败模式

| 错误码 | 条件 | 行为 |
|---|---|---|
| `PROMPT_CONTEXT_MISSING` | 关键动态上下文缺失 | 阻止构造并返回缺失键 |
| `PROMPT_LAYOUT_INVALID` | 多 Agent 模板段数或角色数不匹配 | fail closed |
| `PROMPT_CONTRACT_DRIFT` | 输出契约与 Schema/Handler 不一致 | 测试和 doctor 失败 |
| `WORKER_RECEIPT_MISSING` | 未收齐全部 Worker 回执 | 不完成总 proof |

## 9. EARS 验收标准

1. While Architect Action 被构建，when requirement 或 refine feedback 存在，the
   system shall 将其写入 Architect 实际 Worker prompt。
2. While Developer 进入返工轮，when Critic feedback 存在，the system shall 在
   Inline Developer instruction 中明确给出待修复项。
3. While 多 Agent 阶段运行，when Worker prompt 被生成，the system shall 为每个
   Worker 注入任务上下文、唯一角色和独立输出契约。
4. While Worker 数与模板段数不一致，when Action 被构建，the system shall 返回
   `PROMPT_LAYOUT_INVALID` 而不是复制提示词。
5. While 旧宿主提交当前合法 Result，when 新契约校验，the system shall 兼容接受并
   对缺少的增强字段给出结构化警告。
6. While 同 tick/stage 发生重试，when prompt 日志写入，the system shall 保留所有
   message 版本且不覆盖。
7. While 多 Agent 执行完成，when 总 proof 被验证，the system shall 能验证配置中的
   每个 Worker 都存在独立有效 receipt。
