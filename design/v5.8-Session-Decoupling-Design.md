# Auto-Engineering v5.8 确定性状态与宿主会话解耦设计

> 状态：已批准，待实施｜批准日期：2026-07-29
> 事故证据：Claude Code 真实项目运行 146 Tick 后输入超限
> 事故报告：`incidents/2026-07-29-claude-146-tick-long-run.md`
> 前置设计：`v5.7-Protocol-Kernel-Design.md`、`v5.7-Prompt-Contract-Design.md`
> 实施计划：`v5.8-Session-Decoupling-PLAN.md`

## 1. 决策摘要

采用“确定性状态与宿主会话彻底解耦”方案：

- 工程线程 `EngineeringThread` 是跨会话、跨宿主的长期业务身份。
- `ExecutionSession` 是有预算、可轮换的短生命周期宿主执行租约。
- Core 的 Event Store 是进度、因果、验证和恢复的唯一事实源。
- Claude/Codex 会话历史不是事实源，也不得成为恢复前提。
- Core 不创建宿主会话；达到预算时发出 `session_rollover`，由 Host Adapter
  创建新会话并提交接管回执。
- 新会话只接收 `ResumeCapsule`，不重放完整聊天、工具输出或子 Agent transcript。
- 大型 Agent/审计结果持久化为 `ArtifactRef`，主会话只接收有界摘要和哈希引用。

该方案保持 v5.7 的产品边界：Core 仍不调用 LLM、不复制宿主 Agent Runtime。

## 2. 事故问题与根因

2026-07-29 真实项目运行暴露：

1. 146 个 Tick 在同一 Claude 会话内持续累积，58m input、341m cache、1m output。
2. 152 个 Worker receipt、深度审计及工具长输出反复进入主会话。
3. Architect 追加 B27-B32 时整体替换计划，执行指针错误回到 B1。
4. 投影出现 `done_tasks=85`、`total_tasks=0`、`completion_pct=0`。
5. TypeScript/Vitest 项目被 pytest 执行，`0 tests/exit=5` 仍被判为通过。
6. Gate 文件快照为 SHA-256 空内容哈希，仍被判为通过。
7. 当前 audit 只记录 Gate，不记录 input/cache/output，无法逐 Tick 归因。
8. 目标项目 BEACON 和自动摘要与真实状态不一致，压缩后产生虚假上下文。

直接终止原因是宿主请求超过输入长度上限；系统根因是会话、确定性状态、计划、
验证证据和大产物之间缺少强边界。

## 3. 目标与非目标

### 3.1 目标

1. 任意长度工程轨迹可跨多个短宿主会话推进。
2. 原会话丢失后，新会话仅凭 Event Store、投影和 ResumeCapsule 恢复。
3. 同一轨迹在单会话和多会话执行时产生语义等价的 Core 事件与终态。
4. Core 在达到预算前确定性发出 rollover，避免由模型服务被动拒绝。
5. 已完成批次不得因计划更新重新激活；非法进度投影不得提交。
6. 测试、快照和 Gate 证据 fail-closed，并绑定到实际文件状态。
7. Token、缓存、时间和 Agent 使用可按 session/tick/stage/worker 归因。

### 3.2 非目标

- 不在 Core 内管理 Claude/Codex 对话 API。
- 不把宿主 transcript 复制进 SQLite。
- 不跨宿主迁移不可移植的隐藏推理或模型内部状态。
- 不保证不同模型输出相同，只保证协议、事件和验证语义等价。
- 不以自动摘要替代 Event Store、设计文档或验证证据。
- 不通过降低五层验证、Gate 或 Guardrail 来节省 Token。

## 4. 核心领域模型

```text
EngineeringThread (长期业务身份)
├── LoopEvent[]                 唯一事实源
├── EngineStateProjection      可重建读模型
├── PlanRevision[]             不可变计划版本
├── ArtifactRef[]              大型产物引用
├── UsageLedger[]              成本与容量事实
└── ExecutionSession[]         短生命周期宿主租约
    ├── HostProfile
    ├── BudgetSnapshot
    ├── Action/Result[]
    └── successor_session_id
```

### 4.1 身份边界

| 身份 | 生命周期 | 事实源用途 |
|---|---|---|
| `thread_id` | 从 init 到 done/error | 业务进度、事件和终态 |
| `session_id` | 一个有界宿主会话 | 预算、接管、退出和成本归因 |
| `message_id` | 单个 Action/Result | 幂等和因果 |
| `worker_id` | 单次独立 Worker | 多 Agent 回执与成本 |
| `artifact_id` | 单个不可变产物 | 大结果寻址、校验和审计 |

`thread_id` 不得继续被宿主 conversation ID 隐式替代。宿主 ID 只进入
`extensions.<host>.conversation_id`。

### 4.2 ExecutionSession

```json
{
  "session_id": "uuid",
  "thread_id": "uuid",
  "host": "claude_code",
  "host_session_ref": "opaque-or-null",
  "predecessor_session_id": "uuid-or-null",
  "started_by": "initial|rollover|manual_resume|recovery",
  "budget_policy_id": "default-v1",
  "status": "active|handoff_pending|closed|abandoned",
  "started_at": "timestamp"
}
```

同一线程最多一个 `active` 或 `handoff_pending` session。Core 使用唯一约束和
事件序列保证接管幂等。

## 5. 会话状态机

```text
          start/claim
    ┌──────────────────┐
    ▼                  │
  active ──budget──▶ handoff_pending ──accepted──▶ closed
    │                         │
    │ host lost               │ timeout/retry
    ▼                         ▼
 abandoned ──recover────▶ successor active
```

新增事件：

- `ExecutionSessionStarted`
- `SessionBudgetObserved`
- `SessionRolloverRequested`
- `ResumeCapsuleCreated`
- `ExecutionSessionClaimed`
- `ExecutionSessionClosed`
- `ExecutionSessionAbandoned`
- `UsageRecorded`
- `ArtifactRegistered`
- `PlanPatched`
- `StateInvariantRejected`
- `VerificationEvidenceBound`

所有事件沿用 v1.1 Envelope 的 thread、sequence、causation 和 payload hash。

## 6. Rollover 协议

### 6.1 `session_rollover` Action

控制 Action discriminator 增加：

```json
{
  "action": "session_rollover",
  "reason": "context_soft_limit|context_hard_limit|tick_limit|time_limit|manual",
  "current_session_id": "uuid",
  "capsule": {
    "artifact_id": "uuid",
    "sha256": "hex",
    "schema_version": "1.0"
  },
  "claim_token": "single-use-opaque-id",
  "expires_at": "timestamp-or-null"
}
```

宿主收到后必须：

1. 停止在旧会话继续执行工作 Stage。
2. 关闭或离开旧会话，不把完整 transcript 传给新会话。
3. 创建新宿主会话并加载 Auto-Engineering Skill。
4. 读取并校验 ResumeCapsule。
5. 提交 `session_claimed` Result。
6. Core 返回原线程唯一 active Action。

### 6.2 幂等与竞态

- 同一 rollover 重复提交返回同一 capsule 和 claim token 状态。
- 同一 token 首次合法 claim 成功；完全重复 claim 返回同一后继 Action。
- 不同 session 竞争同一 token 时返回 `SESSION_CLAIM_CONFLICT`。
- 旧 session 在 handoff 后提交业务 Result 返回 `SESSION_NOT_ACTIVE`。
- 新会话启动失败时，原线程保持 `handoff_pending`，不得推进业务 Stage。
- 管理员式强制接管属于高影响恢复操作，必须显式授权并产生审计事件。

## 7. ResumeCapsule

Capsule 是确定性恢复包，不是自由文本 recap。

```json
{
  "schema_version": "1.0",
  "thread_id": "uuid",
  "source_session_id": "uuid",
  "projection_sequence": 146,
  "active_action": {},
  "state_digest": {
    "stage": "developer",
    "active_batch_id": "B27",
    "plan_revision": 4,
    "done_task_ids": ["..."],
    "gate_verdicts": {},
    "open_findings": []
  },
  "required_artifacts": [],
  "policy_snapshot": {},
  "budget": {},
  "issued_at": "timestamp",
  "payload_sha256": "hex"
}
```

约束：

- active Action 必须是已持久化 Action 快照，不重新自由生成。
- done task 默认用 ID/摘要表示，不嵌入历史实现过程。
- 大于阈值的设计、审计和 Worker 结果仅保留 ArtifactRef。
- `required_artifacts` 必须由 Stage Contract 声明，禁止“为保险”附加全部历史。
- Capsule 的 hash、投影 sequence 和 active Action causation 必须同时校验。
- 自动摘要只能作为 `informational_summary`，不得参与状态推进。

### 7.1 状态锚点与摘要隔离

- Event Store/Projector 是业务状态唯一事实源。
- BEACON 是人工维护的设计锚点；过期时产生 drift warning，不覆盖投影。
- recap、`session_summary` 和模型生成摘要只允许进入信息性字段。
- 摘要不得驱动 stage、batch、task 计数、Gate verdict、完成判定或恢复。
- 摘要与投影/Gate 矛盾时，Action 显式报告差异并以结构化事实为准。
- ResumeCapsule 必须从投影和 active Action 构建，禁止从聊天历史反推状态。

## 8. ContextBudget

### 8.1 预算维度

```text
ContextBudgetPolicy
├── max_session_ticks
├── max_session_wall_seconds
├── soft_input_units
├── hard_input_units
├── max_prompt_bytes
├── max_inline_artifact_bytes
├── max_worker_receipt_bytes
├── max_repair_cycles
├── max_workers_per_stage
├── max_workers_per_thread
├── max_plate_audits
└── max_system_audits
```

预算值由 FeatureManifest/宿主 Profile 的版本化策略提供，不在 Skill 中复制。

### 8.2 数据来源

优先级：

1. 宿主原生 usage：input、cache read、cache write、output。
2. Adapter 的 tokenizer/字符估算，并标记 `estimated=true`。
3. 无法估算时使用 Tick、字节和时间上限，禁止把未知当作无限。

### 8.3 决策规则

- 达 soft limit：完成当前 Result 后发出 rollover。
- 达 hard limit：不得编译新的工作 Action，立即发出 rollover。
- 当前 prompt 自身超过硬限制：返回 `ACTION_CONTEXT_TOO_LARGE`，指出最大字段或
  ArtifactRef，禁止截断关键任务和安全规则后继续。
- 修复轮次、Worker 或 Deep Audit 达 soft limit：完成当前原子步骤后 rollover。
- 达 hard limit：发出结构化 pause/rollover；需要扩容时请求用户决策。
- Architect 不得通过追加批次绕过 `max_repair_cycles`。
- Budget Policy 对同一输入必须产生相同决策；模型不得自行决定是否切换。

## 9. 有界上下文编译

Prompt Contract 增加 `ContextSelector`：

```text
StageContract
├── required_context_fields
├── optional_context_fields
├── allowed_artifact_kinds
├── summary_policy
└── size_budget
```

按 Stage 选择：

- Developer：active batch、task、直接依赖、最新 critic finding、相关文件引用。
- Critic：本批次 diff/证据、设计章节引用，不接收其他已完成批次 transcript。
- Component Verifier：组件设计、实现证据、未关闭 finding。
- Deep Audit：全局索引和分片清单；各 Worker 只读取自己的分片。
- Architect repair：开放 finding、已完成 ID 集和 plan revision，不接收所有开发对话。

禁止：

- 把完整 `init-manifest.files` 在每个 Developer Prompt 重复展开。
- 把完整 Gate 日志同时放入顶层、context 和 session summary。
- 将多 Worker 完整输出聚合进 `spawn` 后再回灌主会话。
- 把历史失败摘要机械重复多次。

## 10. ArtifactRef 与多 Agent 交付

```json
{
  "artifact_id": "uuid",
  "kind": "worker_report|audit_report|test_log|design|diff",
  "uri": "project-relative-or-store-uri",
  "sha256": "hex",
  "bytes": 45169,
  "producer": {"session_id": "uuid", "tick": 144, "worker_id": "uuid"},
  "summary": "bounded text",
  "retention": "thread|release|temporary"
}
```

- 完整结果先持久化并计算 hash，再生成 receipt。
- 主 Agent receipt 默认只含 verdict、P0/P1/P2 数、关键 finding ID 和 ArtifactRef。
- Core 校验逐 Worker receipt，但不要求把完整正文嵌入 Action。
- Artifact 不可静默覆盖；相同 ID、不同 hash 返回冲突。
- 临时 Artifact 可按保留策略清理，但事件中的 hash、类型和审计元数据永久保留。

## 11. PlanPatch 与进度不变量

### 11.1 计划版本

Architect 修复周期不得返回“重建后的完整计划”覆盖当前状态，而应提交：

```json
{
  "base_revision": 3,
  "patch_id": "uuid",
  "add_batches": ["B27", "B28"],
  "replace_pending_batches": [],
  "cancel_pending_batches": [],
  "reason_artifact": {}
}
```

已完成 batch/task 是不可变事实。若必须重新打开，使用显式
`ReopenCompletedWork`，要求原因、受影响证据和用户/策略授权。

### 11.2 提交前不变量

- `done_task_ids ⊆ plan_task_ids`
- `done_tasks == |done_task_ids|`
- `total_tasks == |plan_task_ids - cancelled_task_ids|`
- `0 <= done_tasks <= total_tasks`
- active batch 必须存在、未完成、依赖已满足。
- plan revision 单调递增，patch 的 `base_revision` 必须等于 active revision。
- 新 batch/task ID 不得与历史不同 payload 的 ID 冲突。
- 普通 patch 不得重新激活 completed/cancelled work。

违反时不提交投影，记录 `StateInvariantRejected` 并返回稳定错误。

## 12. 验证可信度

### 12.1 工具链选择

TestGate 只接受 Init Manifest/项目配置声明的 runner：

- TypeScript + Vitest：执行版本化的 `pnpm exec vitest run` 或项目权威命令。
- Python + pytest：执行项目权威 pytest 命令。
- 未知或互相冲突：`TEST_RUNNER_UNRESOLVED`，fail-closed。

以下情况必须失败：

- 命令退出码非零。
- 实际收集测试为零，除非项目策略显式声明允许且有独立理由。
- 输出声称 runner A，但命令/解析器来自 runner B。
- 结果解析失败或测试数量未知。

### 12.2 文件快照

Gate 证据必须绑定：

```text
repository_root_realpath
tracked_file_manifest_sha256
selected_files[]
selected_files_sha256
command
tool_version
exit_code
started_at/finished_at
```

非空项目的 selected files 为空、hash 等于空内容 hash、路径逃逸或运行后文件变化，
均不得通过。不同 Gate 可选择不同文件集，但必须声明选择器和理由。

## 13. Usage Ledger 与成本治理

每次宿主执行报告：

```json
{
  "thread_id": "uuid",
  "session_id": "uuid",
  "tick": 146,
  "stage": "developer",
  "worker_id": null,
  "input_units": 0,
  "cache_read_units": 0,
  "cache_write_units": 0,
  "output_units": 0,
  "prompt_bytes": 18391,
  "wall_ms": 0,
  "estimated": false,
  "source": "claude_code"
}
```

要求：

- Usage 是观测事实，不影响已接受 Result 的业务语义。
- 缺失 usage 标记 unknown，不写 0 冒充已采集。
- 报表至少按 thread/session/stage/worker 聚合。
- 记录预算命中、rollover 原因和最大上下文字段。
- `llm-calls.jsonl` 若只记录 Gate，必须更名或扩展，禁止误称 Token 审计。

## 14. Checkpoint 与保留策略

- Event log、active Action、PlanRevision、验证摘要和 Artifact 元数据永久保留。
- EngineState、Prompt 渲染、完整测试日志和临时 Artifact 是可重建或有期限副本。
- 每个 Tick 不保存重复的完整计划、manifest 和历史 Prompt。
- 压缩只作用于副本，不改写事件事实；删除物理产物前验证引用与保留策略。
- `status`、`resume` 和 replay 必须在 Prompt/临时 Artifact 已清理后仍可工作。

## 15. 兼容与迁移

1. v5.7 旧线程恢复时创建 `ExecutionSessionStarted(started_by=manual_resume)`。
2. 旧 Action 无 `session_id` 时仅在唯一 active session 下由兼容层补齐并告警。
3. 旧 Architect 全量 `batch_plan` 先与当前 revision 做三方差异；若涉及已完成任务，
   fail-closed，不自动猜测。
4. `session_rollover` 属 v5.8 控制 Action；不支持的旧宿主返回
   `HOST_CAPABILITY_UNAVAILABLE`，不得继续长会话冒险。
5. 兼容层至少保留一个小版本；真实项目验收完成后再讨论退役。

## 16. 故障恢复矩阵

| 故障 | 期望行为 |
|---|---|
| rollover Action 重复投递 | 返回相同 capsule，不重复建 session |
| 旧会话在 handoff 后提交 Result | `SESSION_NOT_ACTIVE` |
| 新会话 claim 后立即崩溃 | 标记 abandoned，可再次恢复，不推进 Stage |
| Capsule hash 不一致 | `RESUME_CAPSULE_INVALID` |
| Artifact 缺失或 hash 不符 | 暂停相关 Stage，不使用摘要替代证据 |
| usage 缺失 | 业务可继续，但预算采用保守估算并记录 unknown |
| plan patch revision 过期 | `PLAN_REVISION_CONFLICT` |
| 已完成批次被普通 patch 重开 | `COMPLETED_WORK_IMMUTABLE` |
| runner 选错或零测试 | TestGate 失败 |
| 文件快照为空 | Gate 失败 |

## 17. 发布与验收标准

### 17.1 功能

- 至少 150 Tick 黄金轨迹跨三个以上 ExecutionSession 完成。
- rollover 前、后和 claim 中断均可重放到等价状态。
- 修复计划追加后 active batch 指向首个新增待办，不回退已完成批次。
- TypeScript/Vitest 与 Python/pytest 路由均有正反测试。

### 17.2 成本

- 单个宿主会话峰值不得超过配置 hard limit。
- 同一上下文块不得因 Core 编译器在同一 Action 内重复出现。
- 报表可解释至少 95% 已报告 usage；宿主未提供部分单独列 unknown。
- 多会话轨迹的 Core Prompt 字节与 Tick 数近似线性，不得随完整历史呈二次增长。
- 过期 BEACON、重复/矛盾 recap 的负向测试不得改变投影或下一业务 Stage。
- Repair、Worker 和 Deep Audit 达上限时不得继续扩张 Action 或 Agent。

### 17.3 双宿主

- Claude Code 与 Codex 对同一 rollover fixture 产生等价 Core 事件。
- 两个真实安装环境完成包含返工、深审计和 rollover 的中等项目。
- archive smoke、真实安装和真实项目运行继续分层报告。

## 18. EARS 总体验收

1. While 工程线程跨多个宿主会话运行, when 任一会话结束, the Core shall 仅凭事件、
   投影和 Capsule 在新会话恢复相同 active Action。
2. While 上下文达到预算阈值, when 下一 Tick 被构建, the Core shall 发出
   `session_rollover` 且不得继续生成工作 Action。
3. While 已完成任务存在, when Architect 提交修复计划, the Core shall 通过
   PlanPatch 保留完成事实且不得重新激活旧批次。
4. While Gate 验证项目, when runner 错配、零测试、非零退出或空快照发生,
   the Gate shall fail-closed。
5. While Worker 产生大型结果, when 主会话接收回执, the host shall 只获得有界摘要
   与可校验 ArtifactRef。
6. While 宿主报告 usage, when 审计查询运行, the system shall 可按
   thread/session/tick/stage/worker 归因。
