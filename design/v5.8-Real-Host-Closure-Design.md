# v5.8 真实宿主闭环与设计权威设计

> 日期：2026-08-12｜状态：审计修订；基础能力已实现，生产闭环未成立｜任务：T434-T446

## 1. 目标与边界

目标不是继续给 Skill 增加自然语言提醒，而是证明一份显式设计能够经由真实 Claude Code
或 Codex 宿主，从 Architect 稳定推进到业务验证终态，同时不发生 Worker 角色递归、设计
越权、历史状态污染、假验证或无界上下文膨胀。

本阶段只修改 Auto-Engineering Loop。Voice Clone 是受控黄金场景，不修改其业务代码，
也不把其特定目录、组件数量或技术方案写进通用 Core。

## 2. 本轮审计结论

此前 T435-T439 建立了必要基础，但“单元测试通过”被过早表述为“宿主闭环完成”。代码、
协议、测试和真实宿主执行链对照后，确认以下差距：

| 级别 | 差距 | 证据 | 后果 |
|---|---|---|---|
| P0 | Worker 收到了 Coordinator 专属 `spawned` 输出字段 | `action_builder.py` 将 `worker_expected_format` 同时传给 Worker Prompt 和 Team Lead Result | Worker 可能再次检查或调用 `spawn_agent`，直接复现角色递归 |
| P0 | `WorkerInvocation` 未成为生产宿主必须消费的 Action 合同 | Python 编译器只被测试/Fake Host 调用；Skill 仍自行解释 `spawn`、Prompt 和隔离参数 | 机器模型与真实调用可能漂移，测试通过不能证明产品路径正确 |
| P0 | `design_authority` 只有来源标签，没有设计决策账本和结果门禁 | Core 可拒绝 advisory 自称 binding，但不能判断 Architect 是否把 BFF 等建议写入当前计划 | Research 仍可能语义覆盖 Explicit Design |
| P1 | `spawn`、`design_authority`、`expected_format` 在 JSON Schema 中仍是宽泛 object | Action v1.1 无法验证单/多 Worker 调用字段、Worker/Coordinator 结果边界 | 错误直到真实 LLM 执行才暴露 |
| P1 | Fake Host 只执行单 Worker 函数调用 | 未覆盖 proof/challenge、Result validation、Tick、EventStore、resume 和多 Worker 部分失败 | 测试替身形成“自证式通过” |
| P1 | Voice Clone fixture 只断言手写 manifest 常量 | 未携带设计摘录、决策出处、禁止变更和完整生命周期；测试未证明坏计划会被拒绝 | 黄金用例能发现文件漂移，不能证明设计被执行 |
| P1 | Runtime Revision 仍声明 `action_contract_version=1.0`，而 Action schema 为 v1.1 | 代码常量与协议注释不一致，且没有宿主能力协商 | 旧宿主可静默忽略新字段 |
| P1 | Research supplement/archive 可按相同 gap 重复进入 Prompt | 当前只限制条数和单条大小，未按内容摘要去重 | 重复 input、权威混淆和 token 浪费 |
| P1 | 发布验收依赖临时网络解析构建依赖，且真实长跑以固定 Tick 数描述 | PyPI TLS EOF 阻断 archive integration；固定 150 Tick 不能代表业务覆盖 | 环境失败与产品失败混淆，也诱导无效 token 消耗 |

因此，T435-T439 只能记为“自动化基础已具备”，不能作为 T434 的关闭证据。

## 3. 根因

根因不是某一句 Prompt 写错，而是生产边界缺少唯一机器契约：

1. Core 同时输出松散 `spawn` 数据和给人阅读的 `instruction`。
2. Skill/Command 再次从文本推断该如何调用宿主工具。
3. Worker Prompt 和 Coordinator Result 复用同一 `expected_format`。
4. Fake Host 直接调用 Python 编译器，绕过了真实 Skill/宿主解释层。
5. 设计权威只描述“谁更权威”，没有描述“哪些具体决策必须保留”。

这导致自动测试验证的是“参考实现内部一致”，真实产品执行的却是另一条自然语言路径。

## 4. 采用的目标架构

### 4.1 单一 SpawnPlan

所有 spawn Action，无论一个还是多个 Worker，都必须携带同一种严格结构：

```json
{
  "spawn": {
    "contract_version": "1.0",
    "invocations": [{
      "worker_id": "architect-0",
      "role": "architect",
      "prompt_ref": "artifacts/prompts/<sha256>.json",
      "prompt_sha256": "<sha256>",
      "requested_effort": "xhigh",
      "isolation": "fresh_context",
      "capabilities": {
        "may_drive_loop": false,
        "may_spawn_workers": false
      },
      "receipt_path": ".ae-state/spawn-proofs/<token>.json"
    }]
  }
}
```

单 Worker 不再走 `subagent_prompt` 特例；`instruction` 只作人类诊断文本，不是执行事实源。
Host Driver 必须逐项消费 `spawn.invocations[]`，不得重新推导 Prompt、effort 或隔离方式。

Host Adapter 在通过 Action Schema 与 `SpawnPlan` 校验后，按宿主平台额外物化
`host_execution.workers[]`。每项包含规范 `worker_id`、唯一 `receipt_path`、receipt 模板和
attestation 模板；两类模板初始均为 `pending`，只能在原生 Worker 成功后转为 `completed`。
Codex 的隔离证据固定为 `fork_turns=none`，Claude Code 固定为
`fresh_context`，能力摘要由 invocation 计算。原生 Agent/thread UUID 只能写入
`native_worker_handle`，不得替换规范 Worker ID。该对象属于 Host 映射产物，不反向写入
Core ActionSnapshot，避免宿主差异污染确定性协议事实。

### 4.2 分离四类输出

| 类型 | 产生方 | 可包含内容 | 禁止内容 |
|---|---|---|---|
| `WorkerOutcome` | Worker | 当前角色业务结果、证据引用、状态 | `spawned`、总 proof token、Tick/Loop 操作 |
| `WorkerAttestation` | Host Driver | invocation、实际隔离、有效能力、模型/effort、Prompt hash、时间与状态 | 业务结论 |
| `CoordinatorAssembly` | Coordinator | 多 Worker 合并、冲突和缺失项 | 伪造 Worker 结果 |
| `StageResult` | Coordinator | `spawned`、总 proof、当前 Stage 结果 | Worker 自行声明的宿主事实 |

Core 只接受与 active Action、invocation id、Prompt hash、receipt digest 绑定的 StageResult。

### 4.3 三层强制等级

不能把宿主无法技术强制的事项写成 Core 已强制：

- **Core 可强制**：Schema、因果身份、Prompt hash、能力需求、receipt、设计决策覆盖、幂等。
- **Host 可证明**：实际使用的原生工具、隔离参数、有效 effort、可见能力摘要和调用状态。
- **Worker 行为约束**：不执行 Loop、不 spawn。由最小 Prompt 约束并由 outcome/attestation 检测，
  但不能仅凭 Prompt 宣称已安全隔离。

Codex 的 `fork_turns="none"` 只表示不继承会话 turns，不等于不注入系统规则、AGENTS 或工具。
因此发布证据必须记录有效能力摘要，而不是将 `fork_turns` 当作完整沙箱证明。

### 4.4 设计决策账本

`DesignAuthorityPolicy` 继续定义来源优先级；新增 `DesignDecisionLedger` 描述可检查的语义：

```json
{
  "decision_id": "VC-ARCH-001",
  "source_ref": "design.md#4.1",
  "scope": "current",
  "statement": "V1 为纯前端 React SPA，直接调用 MiniMax API",
  "classification": "binding",
  "change_policy": "explicit_user_approval",
  "prohibited_promotions": ["future_bff_to_v1_requirement"]
}
```

范围只允许 `current`、`known_issue`、`future`、`out_of_scope`。Gap Scan 只有在设计缺失、
内部矛盾或无法实施时才能创建 gap；`future` 和 `known_issue` 不能自动升级为当前阻断项。

Architect/Refine Result 必须逐项返回 `decision_impacts`：`preserve` 或带批准引用的 `change`。
Core 可以检查覆盖和批准链，但不能可靠地从任意自然语言自动提取全部语义；无账本时应明确
标记 `semantic_enforcement=partial`，不得冒充确定性门禁。

设计权威上下文必须贯穿 Architect、Developer、Critic 和 Verifier，而不是只在前置阶段出现。

### 4.5 上下文去重

Research、supplement 和 archive 先规范化为 `{gap_id, content_sha256, sources, authority}`，按
`gap_id + content_sha256` 去重。相同内容只传一次并保留来源列表；当前 Stage 只接收直接相关
决策和未关闭义务，禁止重复整份设计、研究全文或历史 Action。

## 5. 验收架构

### 5.1 四层证据

| 层 | 目的 | 必须覆盖 | 不能证明 |
|---|---|---|---|
| L1 协议单元 | 证明 Schema、编译器和门禁确定性 | 正/负 Schema、Worker/Coordinator 分离、authority ledger | 原生宿主真的照做 |
| L2 轨迹仿真 | 证明完整 Action→Result→Tick→EventStore | 单/多 Worker、proof、重试、崩溃恢复、重复/迟到结果 | 真实 LLM/工具行为 |
| L3 产品 Canary | 证明候选插件和原生工具可用 | 安装、发现、Architect→Developer→Critic、一次恢复 | 中长项目最终完成 |
| L4 完整黄金项目 | 证明设计到业务终态 | 双宿主同一输入、最终 build/test、设计覆盖、成本 | 其他未知项目全部正确 |

### 5.2 故障矩阵

L2 至少注入：Worker 角色违规、Prompt hash 漂移、容量一次恢复/持续耗尽、timeout、畸形
outcome、多 Worker 部分成功、写 receipt 后 Coordinator 崩溃、重复 Result、迟到 Result、恢复
后 capability 变化和 research 越权计划。每个故障必须有确定的 `continue/wait/fail/gate` 结果。

### 5.3 黄金场景包

Voice Clone 黄金包由设计摘录、决策账本、义务集合、禁止变更、期望生命周期和业务验收
命令组成。断言语义不变量，不固定 LLM 必须生成相同批次数或相同措辞；11 个组件、17 个
测试文件和 127 个用例作为原设计目标保留出处，但跨宿主等价以决策覆盖、最终业务产物、
Gate verdict 和未批准变更为准，不要求字节级计划一致。

### 5.4 发布门禁

- 每次提交：L1 + L2，串行、无网络、覆盖率与静态检查。
- 每个 RC：双宿主 L3；候选 Build Identity、全新项目状态和宿主能力清单必须入证据包。
- 发布前：每个宿主至少一次 L4；完整业务 build/test、零非预期停顿、零设计越权。
- 150 Tick 仅保留为确定性模拟压力测试，不再要求真实 LLM 为凑 Tick 消耗 token。
- 成本以场景预算和 usage 完整性门禁；缺失 usage 时为 `measurement_incomplete`，不能通过。
- archive smoke 必须与产品验收分栏。网络依赖失败标记 environment failure，不可算产品通过；
  发布制品验收应使用预构建/锁定依赖或受控 wheel cache，避免临时解析构建后端。

## 6. 兼容与迁移

1. 先增加可选 `spawn.invocations[]` 并双写旧字段，当前 v1.1 宿主仍可读取旧结构。
2. 新 Host Driver 回传 capability/attestation；Core 在 capability negotiation 后优先严格路径。
3. 双宿主 L3 通过后，将 `isolated_worker_invocation` 标为 spawn Stage 必需能力。
4. 下一协议次版本才移除单 Worker `subagent_prompt` 特例；旧在途 Action 仍按其 Runtime Vector
   完成，不在活动 Action 中途升级。
5. `action_contract_version` 与实际 Schema 统一；不支持严格能力的旧宿主必须在 spawn 前
   fail-closed，不得静默忽略。

### 6.1 插件运行时来源

插件元数据、Skill、Core Python 包与 `uv.lock` 必须来自同一插件根。源码 Marketplace
复制出的虚拟环境如果其 entrypoint shebang 指向插件根之外，视为不可信且禁止执行；宿主应
在插件专属隔离目录按锁文件创建运行时。全局 `ae` 不具备 Build Identity 绑定，不作为降级
路径。活动 Action 的 Runtime Vector 与当前运行时不兼容时保持 fail-closed，不用 SemVer
相同掩盖合同或制品漂移。

### 6.2 本机安装来源隔离

开发工作区只允许作为 Release 构建输入，不得成为产品 Marketplace 或运行时依赖。安装器
必须把自包含归档安全解压到开发目录之外、以 `build_id` 命名的持久目录，再由 Codex 注册
该目录内 Marketplace。安装后分别验证 Marketplace 根、插件根、`.ae-runtime` 解释器、
入口脚本和 `auto_engineering` import origin；任一真实路径落入开发工作区即 fail-closed。
不可变 Release 资产继续按 `build-info.json` 校验且禁止符号链接，安装后可重建的
`.ae-runtime` 不进入内容摘要，按独立来源规则验收。

## 7. EARS 验收

- While spawn Action 被编译, when Worker Invocation 产生, the system shall 对单/多 Worker
  使用同一严格结构，且 WorkerOutcome schema 不含 Coordinator 专属字段。
- While Host 执行 Worker, when 原生调用完成, the host shall 产生与 Action、Prompt hash、
  隔离和有效能力绑定的 attestation；缺失或不一致时 Core 不推进。
- While Host Adapter 映射严格 spawn Action, when 宿主执行三 Worker, the host shall 以
  `host_execution.workers[]` 为证明模板唯一事实源，并将原生句柄与规范 Worker ID 分离。
- While EventStore projection 与 active ActionSnapshot 完整, when legacy checkpoint 数为零,
  the Core shall 从事件事实源恢复；若协议不兼容，错误必须列出线程、Action 和差异向量。
- While 插件缓存包含从源码复制的虚拟环境, when entrypoint shebang 指向插件根之外,
  the launcher shall 拒绝该环境并按当前插件锁文件创建隔离运行时，禁止调用全局旧 `ae`。
- While Research 与 binding decision 冲突, when Architect Result 被验证, the Core shall
  要求 `decision_impacts` 和用户批准引用，否则拒绝激活计划。
- While Fake Host 执行完整轨迹, when 任一故障被注入, the final projection shall 按规定
  恢复或 fail-closed，且不得只返回孤立的函数调用成功。
- While 同一黄金设计在 Claude Code 与 Codex 运行, when 完整业务 Gate 结束, both hosts
  shall 保留同一 binding decisions、产生等价 verdict 且不要求相同自然语言计划。
- While 真实 LLM 场景运行, when usage 超预算或测量缺失, the release shall 失败或标记
  `measurement_incomplete`，不得以固定 Tick 数代替成本治理。
