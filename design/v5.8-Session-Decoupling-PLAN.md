# Auto-Engineering v5.8 会话解耦实施计划

> 状态：待实施｜批准日期：2026-07-29
> 设计：`design/v5.8-Session-Decoupling-Design.md`

## 1. 目标、顺序与约束

目标是先恢复真实运行验证可信度，再实现会话解耦、有界上下文和成本审计，最后通过
双宿主真实项目门禁。

实施顺序固定：

```text
Phase 64 可信度止血
→ Phase 65 会话解耦
→ Phase 66 上下文/产物/成本治理
→ Phase 67 双宿主真实验收
```

Phase 64 完成前，不再把无人值守中等规模真跑作为发布证据。每个功能或缺陷任务采用
TDD；串行执行 pytest；未经授权不提交、不推送、不发布。

## 3. Phase 65：确定性状态与宿主会话解耦

### T308：ExecutionSession 与事件契约

新增 Session 模型、事件、schema、Projector 和唯一 active session 不变量。

**EARS：** While thread 跨会话运行, when session 状态变化, the Event Store shall
原子记录转换，并从事件重建相同 session projection。

### T309：ResumeCapsule

新增 Capsule schema、builder、store、hash 校验和 ArtifactRef 列表。

**EARS：** While active Action 已持久化, when rollover 创建 Capsule, it shall
引用同一 Action 和 projection sequence，且不包含完整 transcript。

增加字段白名单、尺寸上限、缺失 Artifact、hash 损坏和 replay 测试。

### T310：ContextBudget 与 rollover 决策

实现 BudgetPolicy、usage/estimate 输入、soft/hard limit 和确定性决策。

**EARS：** While budget 达到 hard limit, when Kernel 构建下一 Action,
the system shall 只返回 `session_rollover`。

阈值来自 FeatureManifest/HostProfile；Skill 和模板不得复制默认数字。

### T311：Rollover Action/Result 幂等恢复

扩展 Protocol Envelope discriminator、claim token、错误码和单 Tick 事务。

覆盖重复投递、重复 claim、竞争 claim、旧 session 晚到 Result、新 session 崩溃及恢复。

### T312：Claude/Codex 会话适配

更新两个 Host Adapter、共享 Skill/Command 和规则模板：

- 旧会话停止执行工作 Action。
- 新会话只加载 ResumeCapsule。
- 提交 claim 后获取唯一 active Action。
- 不支持 rollover 的宿主 fail-closed。

两个宿主不得在 Core 中出现分叉业务逻辑。

### T313：Phase 65 验收

- 150+ Tick fixture 跨至少三个 session。
- rollover 各边界故障注入通过。
- 单会话基准与多会话 Core 事件/投影/verdict 语义等价。
- v5.7 旧线程兼容导入仅告警一次。

## 4. Phase 66：有界上下文、产物引用与成本审计

### T314：Stage Context Selector

扩展 StageContract，声明 required/optional fields、Artifact kind 和字节预算；Compiler
拒绝未声明历史和重复结构。

**EARS：** While Developer Action 被编译, when 历史有 100 个已完成批次,
the prompt shall 只包含 active batch、直接依赖、最新 feedback 和必要引用。

### T315：ArtifactRef 与精简 Worker Receipt

新增 Artifact schema/store、不可覆盖 hash、receipt 尺寸门禁及多 Agent/审计适配。

**EARS：** While Worker report 超过 inline 阈值, when 交付完成, the host shall
收到 ArtifactRef 与有界摘要，Core shall 仍验证独立 worker receipt。

### T316：逐 Tick Usage Ledger

扩展 Host SPI `collect_usage()` 和审计模型；未知值使用 null/unknown，不写零。

覆盖 Claude/Codex 原生 usage、估算回退、Worker、缓存字段、聚合和 PII 安全。

### T317：Checkpoint 与审计保留策略

拆分永久事实、可重建投影和临时产物；实现 dry-run 清理、引用完整性检查和恢复测试。
删除物理产物仍属于需单独授权的操作，本任务只实现机制和测试，不自动清理用户数据。

### T318：Phase 66 成本与完整性验收

- Prompt 字节随 Tick 近似线性，不随完整历史二次增长。
- 每 session 不超过 hard limit。
- Usage 报表按 thread/session/stage/worker 聚合。
- 已报告 usage 的归因率不低于 95%，unknown 单独列示。
- 清理可重建副本后 status/resume/replay 仍通过。

## 5. Phase 67：双宿主真实项目发布门禁

### T319：中等规模双宿主真实验收

在隔离目录分别安装候选包，执行包含开发、返工、深审计和 rollover 的 TypeScript
真实项目。不得使用本项目源码路径或历史 checkpoint。

### T320：故障恢复与成本基线

在 soft limit、handoff pending、claim 后三个位置注入宿主退出，验证恢复、事件等价、
无重复副作用和成本报告完整。

### T321：v5.8 发布收口

执行：

- Phase 64-67 专项测试；
- 全量 pytest、覆盖率、Ruff、mypy、规则同步和 metadata；
- 双宿主 archive acceptance；
- 双宿主真实安装；
- 中等规模真实项目；
- 制品内容和 SHA-256。

只有全部通过且无 P0/P1 未关闭项时，才可请求用户授权 commit、push 和发布。

## 6. 跨任务完成定义

每个任务完成必须同时具备：

1. 可复现 RED 证据。
2. 最小实现和 GREEN 证据。
3. 事件/schema/兼容边界测试。
4. 相关回归、Ruff 和 mypy。
5. Tracker 状态与验证数字更新。
6. 无密钥、临时调试、假通过或未解释 warning。

不得以“提示词更短”“运行未报错”或“宿主自动 recap”替代确定性验收。
