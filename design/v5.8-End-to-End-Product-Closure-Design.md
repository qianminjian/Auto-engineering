# v5.8 端到端产品闭环设计

> 日期：2026-08-25｜状态：已批准｜适用范围：后续全部 Loop 工程实施与验收

## 1. 决策

Auto-Engineering 后续只有一个 P0 产品目标：

> 用户从开发目录执行一次 `$auto-engineering --design-doc <path>`，安装后的宿主必须从设计输入持续运行到 `TERMINAL`；除真实产品决策、明确资源等待或不可恢复环境故障外，不得要求用户理解或续接内部流程。

现有 Tick、EventStore、Gate、Result、Host Runtime 和审计能力均是实现手段，不再作为独立的产品完成标准。任何局部能力只有被真实端到端轨迹使用并证明时，才能成为产品完成证据。

## 2. 为什么需要纠偏

现有总体设计已经要求一次启动、连续执行和真实宿主验收，但实施过程长期按组件关闭任务：每次真跑暴露一个边界问题，就增加一个字段、校验器、恢复分支或回归测试。结果是内部测试持续增长，真实 L4 仍反复在前序环节停止。

主要矛盾不是控制不足，而是完成定义错误：

- 局部模块通过被误认为产品推进；
- archive smoke 和内部轨迹不能证明真实宿主能完成用户任务；
- 真跑故障按报错位置修复，没有回溯其所属的端到端职责；
- Agent 被要求复制机器事实，增加了格式错误、上下文消耗和恢复复杂度；
- 同一设计在不同阶段被重复解释，设计、计划、实施和验收可能发生语义漂移。

## 3. 四条不可分割的产品主线

### 3.1 唯一设计工程模型

设计文档首次进入 Loop 时，Core 建立稳定的工程模型，至少表达：设计来源、需求、设计决策、缺口、实施任务、依赖、验收条件和证据引用。

Gap Scan、Architect、Developer、Critic 和 Verification 必须消费并增量更新同一模型，不得各自重新建立一套互不关联的章节、任务或完成事实。

必须形成可追溯链：

```text
设计要求 -> 缺口/决策 -> 实施任务 -> 代码变更 -> 验证证据 -> 最终结论
```

自然语言标题只用于展示；稳定身份和关系由 Core 维护。

### 3.2 连续 Host Runtime

Core 继续保持单 Tick 和确定性事务；Host Runtime 负责把多个 Tick 组合成一次用户可感知的连续运行。

Host Runtime 必须自动完成：获取 Action、调用原生 Agent、执行工具、装配结果、提交 Core、取得下一 Action、处理上下文隔离和从持久化状态恢复。Tick、Result、journal、checkpoint 和子代理证明均不得成为日常用户操作。

合法退出仅包括：

1. `TERMINAL`；
2. 需要用户选择且会改变产品设计的 `WAIT_USER`；
3. 外部资源暂不可用且宿主无法自动等待的 `WAIT_RESOURCE`；
4. 已证明不可恢复并给出可行动诊断的 `ERROR`。

模型输出格式错误、可修复验证失败、阶段切换、会话压缩或普通 Agent 失败均不是用户退出条件。

### 3.3 推理结果与机器事实分离

Agent 只提交需要推理的业务语义，例如设计缺口、实施结果、审查发现和验证解释。

Action 身份、设计摘要、状态、计数、覆盖集合、因果关系、receipt、attestation 和协议封装由 Core 或 Host Runtime 从当前事实生成。不得要求模型复制这些机器事实来证明自己正确。

### 3.4 真实产品验收

发布完成只由独立安装制品中的真实宿主轨迹证明。测试层级含义固定：

| 层级 | 证明内容 | 能否证明可发布 |
|---|---|:---:|
| L1 | 函数、schema 和状态不变量 | 否 |
| L2 | 插件内确定性轨迹与故障注入 | 否 |
| L3 | 独立安装后的宿主 Canary | 否 |
| L4 | 真实设计项目从单命令运行到 `TERMINAL` | 是 |

L1-L3 是定位和防回归工具；只有双宿主 L4 达标后，候选版本才满足产品目标。

## 4. 实施战略

后续不再以新增 Phase、T 编号或局部控制能力表示主线进度。所有工作归属唯一交付任务 `P0-E2E`，四条主线只是该任务的工作面，不能单独宣布产品完成。

每次真跑失败必须先完成根因归属：

| 归属 | 核心问题 |
|---|---|
| 设计工程模型 | 系统是否始终知道做什么、为什么做、如何验收？ |
| Core | 是否给出唯一、确定且可恢复的下一状态？ |
| Host Runtime | 是否自动执行和续接，而未把内部工作交给用户？ |
| Agent 边界 | Agent 是否只承担推理和工程工作？ |
| 验收 | 证据是否经过独立制品和真实宿主生产路径？ |

修复必须覆盖从故障根因到 L4 的完整路径，禁止只修改最终报错点。若一项改动不能直接提高单命令到达 `TERMINAL` 的概率，或不能防止已证实的主链回归，则不进入当前 P0。

## 5. 冻结边界

在 `P0-E2E` 关闭前，冻结：

- 与已知主链故障无关的新治理能力；
- 新的用户可见管理命令；
- 只增加字段、错误码或校验器而不修复端到端职责的改动；
- 以单元测试数量、覆盖率或 archive smoke 宣布阶段完成；
- 每份真跑报告单独创建一批互不关联的点状任务。

安全、数据损坏和不可逆错误仍保持 fail-closed，但控制完美化不得优先于主链闭环。

## 6. P0-E2E 验收标准

1. While 独立内容寻址制品已安装, when 用户在空项目执行一次设计驱动命令, the product shall 自动完成配置、设计扫描、规划、开发、审查、修复和验证并到达 `TERMINAL`。
2. While Action 仍可自动执行, when 一个 Tick、阶段或模型上下文结束, the Host Runtime shall 自动取得并执行下一 Action，不要求用户发出 continue、resume 或内部 Result 命令。
3. While 设计文档贯穿多个阶段, when 任一 Agent 产生缺口、任务、代码或验收结论, the system shall 将其绑定到同一稳定设计工程模型并保持可追溯。
4. While Agent 返回语义内容, when Host Runtime 提交 Result, the product shall 自动注入机器事实，且模型不需要复制 Core-owned 字段。
5. While 可恢复的格式、验证、Agent 或会话故障发生, when Runtime 处理故障, the run shall 在有界策略内自动修复或续接，不退出为用户操作。
6. While Claude Code 与 Codex 使用同一 Build 和设计输入, when 双宿主 L4 完成, both runs shall 到达等价 Core 终态，且均无非预期人工续接。
7. While L4 尚未通过, when 生成发布结论或更新跟踪表, the release and `P0-E2E` shall 保持未完成，不得由任何 L1-L3 证据替代。

## 7. 退出标准

`P0-E2E` 只有在以下证据同时存在时关闭：

- 独立安装制品与开发目录无运行时依赖；
- Claude Code 和 Codex 各完成一次完整 L4；
- 两条轨迹均从单次用户命令到 `TERMINAL`；
- 零非预期人工续接、零手工协议修复、零旧计划误续作；
- 设计—任务—代码—验证追踪完整；
- 中断恢复与上下文成本满足已批准预算；
- 相关 L1/L2 回归、静态检查和覆盖率门禁继续通过。

任何一项缺失都表示产品目标尚未完成。

## 8. 2026-08-25 L4 证伪：执行包不闭合

最新 Voice Clone 真跑在 Gap Scan 以 `SECTION_FINDING_UNKNOWN` 停止。根因不是设计内容或
模型偶然格式错误，而是三种投影不一致：Canonical Action 含 `design_sections`，Prompt
Contract 未选择该字段，compact Action 又隐藏 `context`，但 Result Contract 要求宿主返回
其中的内部 `section_id`。既有端到端测试直接读取 Canonical `action["context"]` 后替宿主
拼装 Result，因此没有经过真实产品可见边界，Milestone 4 的既有“离线终态”证据被证伪。

后续所有 Action 必须满足 **Host Execution Package Closure**：宿主生成合法语义结果所需的
全部输入、引用、枚举和修复信息，只能来自 compact Action、Coordinator/Worker Prompt
Artifact、work files 与机器 operations；不得读取 Canonical Action 私有状态补全。

## 9. Host Execution Package 唯一执行契约

每个 Action 的宿主执行包由同一次 Action 编译产生：

```text
Canonical Action
  -> Host Execution Package
       |- compact control envelope
       |- coordinator/worker prompt artifacts
       |- agent-owned semantic result contract
       |- human reference map
       |- finalize/validate/submit operations
       `- repair contract
```

必须自动验证闭包：Result Contract 中每个 Agent-owned 字段所需的引用和枚举，必须存在于
对应 Prompt Artifact 或显式工作文件；任何测试、Skill 或 Host Adapter 不得越过执行包读取
`TickOrchestrator._state`、Canonical `context` 或 EventStore 来替 Agent 生成结果。

## 10. Section 双身份边界

- Agent 只消费和返回唯一、可读的 `section_ref`，例如 `5/api-layer#1`。
- 宿主可展示 `section_ref + title`；EngineeringModel 必须将裸 ref、标题和该可读标签解析到
  同一内部 ID，未知或歧义引用仍 fail-closed。
- Core 内部 `section:<hash>` 只用于事件、追溯和稳定绑定，不再要求 Agent 复制。
- Execution Package 明确交付 `section_ref`、标题和文档引用；Assembler 使用同一模型确定性解析
  为内部 `section_id`，并生成 digest、coverage 与计数。
- 迁移期只读兼容合法 `section_id`；未知引用一次返回全部可读 expected refs，禁止猜测序号。

## 11. Result 全链修复事务

修复边界必须覆盖 Assembler 与 Core 两侧：

```text
semantic payload
  -> assembly_rejected -> same Action repair
  -> prepared
  -> core_rejected -> same Action repair
  -> accepted
```

`assembly_rejected` 必须持久化 Action identity、payload、完整 violations、已有 Worker outcomes
和 repair attempt。Runtime 只能创建新的 Action-scoped context 修复 Coordinator payload，不能
推进 Core、重复 Worker、继续提交陈旧 Result 或要求用户重新初始化。

修复 Action 即使保留 Canonical `spawn` 以供审计，Host Execution Package 也不得再次暴露
`workers` 启动合同；finalize 继续引用首次完成的 outcomes 工作文件。任何后续拒绝不得覆盖
`outcomes_fingerprint`、outcomes 或 Worker 完成时间，否则会把合法修复变成永久冲突。

Architect Result 的预校验必须覆盖下一 Action 构建所需的章节引用；不得先接受并持久化计划，
再在 Developer Action 构建时才发现引用不可解析。

ProjectProfile 对标准 `pyproject.toml` 中已声明的 pytest、Ruff 和 mypy 配置必须生成可执行
命令；纯 Python 项目的 build 能力使用确定性的源码编译检查或显式 N/A。缺失这些机器事实
不得让 Developer 反复修改业务代码“补配置”，而应由 Profile/Setup 一次解决。

## 12. 黑盒产品验收规则

离线双宿主轨迹必须从安装制品的公开入口开始，只消费 Host Execution Package，并覆盖至少
一次 Assembler 拒绝、一次 Core 拒绝、一次进程恢复和一次 Critic P1 返工。若测试读取
Canonical `context` 或私有状态生成 Result，该证据无效。只有此黑盒轨迹与真实双宿主 L4
都到 `TERMINAL`，才允许恢复 Milestone 4/5 的完成状态。

### 12.1 质量门禁不得依赖墙钟耗时

审计可信度只能由覆盖、证据、追溯和结果结构判断。模型速度、缓存命中和项目规模都会改变
耗时，因此“少于 N 秒且零发现”只能作为观测信号，禁止触发 Result 拒绝或重复 Agent 调用。
相同语义候选没有新增反馈时，Runtime 不得再次付费执行同一 Action。

## 13. Action 成本归因与往返约束

宿主 receipt 的 `input_tokens` 是一次 Action 内模型多轮推理与工具调用的累计值，不能直接
解释为 Coordinator Prompt 的静态长度。Core 必须同时保留 Prompt/Envelope 字节数、宿主
context 数和 token usage，区分“执行包膨胀”与“Action 内往返过多”。

成本优化顺序固定为：兼容结构差异由 Assembler 本地归一；Assembler、预校验和 Core 拒绝
统一返回同一 Action 的定向 repair；Setup/Developer 一次获得必要写入及受控网络能力；Prompt
只传 compact Action 和内容寻址引用；最终以阶段 context 次数、累计 usage 和终态共同验收。
不得为了降低表面 token 数删减设计语义，也不得为机械格式偏差重跑完整业务 Action。

While Action 的公开执行包保持不变, when token usage 明显增长, the product shall 将增长归因到
具体 context 和工具往返，并优先消除重复 Action 或可本地处理的修复，不重新注入历史会话。

## 14. 纵向测试与真跑故障回放

过去的“模块全绿、真跑即停”表明行覆盖率不能代表产品闭环。自本节起，L2 验收必须至少有
一条公开入口的纵向轨迹：`Canonical Action → Host Execution Package → Prompt Artifact →
Worker/Coordinator outcome → Assembler → result.json → Core Tick`。测试不得读取
`TickOrchestrator._state` 或 Canonical `context` 替宿主生成结果；语义输入只能来自执行包、
Prompt Artifact 和工作文件。

每个关键故障必须形成可重放 fixture，并覆盖以下正交维度：

| 维度 | 最小场景 |
|---|---|
| Worker 状态 | completed、timed_out、failed、cancelled |
| Coordinator 结果 | 合法、空、缺必填字段、类型错误、旧 Action 文件 |
| 事务边界 | 首次 finalize、Assembler 拒绝、Core 拒绝、进程恢复、accepted |
| 宿主差异 | Codex 与 Claude 的同一语义 Action 和等价终态 |
| 资源与成本 | context 超时、容量不足、预算耗尽、重复往返和 token 归因 |

验收同时检查 Result、Outcome Journal、ExecutionControl、Stop Report 和 EventStore 事件，
不能只检查最终错误码。覆盖率、单元测试数量和 archive smoke 只能作为支撑证据，不能关闭
L3/L4；真实宿主发现的问题必须先转为回放 fixture，再允许修复代码。
