# P0-E2E 端到端产品闭环实施计划

> **执行要求：** 使用 `executing-plans` 按顺序实施。每个里程碑先建立真实 RED，再以同一生产轨迹 GREEN；局部测试通过不能关闭里程碑。

**目标：** 独立安装后的 Codex 与 Claude Code 从一次设计驱动命令持续运行到等价 `TERMINAL`，不要求用户续接内部协议。

**架构：** 保留确定性单 Tick Core；用稳定工程模型贯穿设计、任务和验证；Host Runtime 连续驱动；Agent 只返回推理语义，Core/Runtime 绑定机器事实。不增加用户管理命令，不建立第二内核。

**权威规格：** `design/v5.8-End-to-End-Product-Closure-Design.md`

---

## 实施纪律

1. `P0-E2E` 是唯一交付任务，下面五项是同一任务的纵向里程碑，不单独代表产品完成。
2. 真跑失败先归属工程模型、Core、Runtime、Agent 边界或验收链，再修复从根因到生产入口的完整路径。
3. 冻结与主链无关的新治理能力、用户命令和字段级完美化。
4. 每次 GREEN 都必须重跑从用户入口到当前阶段的轨迹；不得让测试读取 Core 私有状态拼出正确 Result。
5. 只有双宿主 L4 达到 `TERMINAL` 后才更新发布结论。

## Milestone 2：统一设计工程模型并移除 Agent 的机器事实责任

**目的：** 解决同一设计在 Gap、Architect、Developer 和 Verification 被重复解释的问题，同时消除模型复制协议事实导致的格式故障和 Token 浪费。

**Files:**

- Create: `auto_engineering/loop/engineering_model.py`
- Create: `tests/test_engineering_model.py`
- Modify: `auto_engineering/loop/action_builder.py`
- Modify: `auto_engineering/loop/tick_orchestrator.py`
- Modify: `auto_engineering/host/execution_assembler.py`
- Modify: `auto_engineering/prompts/roles/gap_scan.md`
- Modify: `auto_engineering/loop/actions.py`
- Modify: `auto_engineering/loop/stage-result.schema.json`
- Modify: `tests/test_host_execution_assembler.py`
- Modify: `tests/test_prompt_contracts.py`

**实现：**

- `EngineeringModel` 以设计 digest 和稳定 section ID 为根，记录 section → gap/decision → task → evidence 的关系；它是现有 `DesignDoc`、Gap、Plan 和 EventStore 事实的统一投影，不是第二状态机。
- Gap、Architect、Developer、Critic 和 Verification 只消费这套稳定 ID，不再各自从展示标题推导章节集合。
- Agent 输出合同仅包含推理语义：gap 内容及按稳定 section ID 标识的 findings。
- Assembler 从 active Action 自动生成 digest、coverage、scanned count、blocking summary、因果身份和证明字段；Agent 无法覆盖这些字段。
- 真正缺失、重复或未知的 section finding 在 journal 写入前一次返回完整诊断。

**EARS：** While Agent 返回完整语义 findings, when Assembler 构建 Result, the product shall 从 active Action 注入全部机器事实，并保持设计—缺口—任务—证据的稳定追溯。

## Milestone 3：让候选 Result 先被 Core 接受，再成为完成事实

**目的：** 解决“错误结果已经 committed，Core 随后拒绝并终止”的事务倒置，使可恢复问题在一次用户调用内自动修复。

**Files:**

- Create: `auto_engineering/host/outcome_journal.py`
- Create: `tests/test_outcome_journal.py`
- Modify: `auto_engineering/host/execution_assembler.py`
- Modify: `auto_engineering/cli/dev_loop.py`
- Modify: `auto_engineering/loop/tick_orchestrator.py`
- Modify: `auto_engineering/loop/execution_control.py`
- Modify: `auto_engineering/host/runtime_driver.py`
- Modify: `auto_engineering/host/supervisor.py`
- Modify: `tests/test_cli_dev_loop_tick.py`
- Modify: `tests/test_execution_control.py`
- Modify: `tests/test_host_supervisor.py`

**实现：**

- Result journal 采用 `prepared → accepted` 或 `prepared → rejected → repaired`，只有 Core 的 `ResultAccepted` 事件可触发 accepted。
- rejected 保留 active Action 和已完成 Worker outcome，不推进业务状态、不重新 spawn Worker。
- repair 执行包隐藏 Worker 启动合同但保留原 outcomes 引用；后续 assembly rejection 必须保留 Worker fingerprint、outcomes 和完成时间。
- 格式、覆盖和可修复语义问题映射为内部 `RESULT_REPAIR_REQUIRED + CONTINUE`，Runtime 自动重做 Coordinator/inline 结果并使用现有有界 repair budget。
- Assembler、`--tick --validate` 预校验和 Core 提交拒绝统一进入上述事务；兼容性类型差异先由 Assembler 本地归一，禁止为机械格式偏差重跑完整业务 Action。
- Architect 预校验必须使用统一 EngineeringModel 解析所有 `design_sections`，并证明下一 Developer Action 可构建后才允许接受计划。
- LocalProbe 必须从标准 Python 工具配置生成 pytest/Ruff/mypy/build 能力；能力缺失进入 Setup/Profile 修复，不转化为业务 Worker 重试。
- 用户只会看到 `TERMINAL`、真实设计选择 `WAIT_USER`、无法自动等待的资源问题或预算耗尽后的可行动错误。
- prepare、Core 接受、journal accepted 任一边界进程中断后均从同一事实幂等恢复。

**EARS：** While candidate Result 可修复但未被 Core 接受, when Runtime 处理拒绝或中断, the product shall 在同一用户调用内修复并继续，且不得把候选写成完成事实或重复执行 Worker。

**验证：**

```bash
uv run pytest tests/test_outcome_journal.py tests/test_cli_dev_loop_tick.py tests/test_execution_control.py tests/test_host_supervisor.py tests/test_host_execution_assembler.py -q --no-cov --timeout=60
uv run pytest tests/test_p0_e2e_product_closure.py -v --no-cov --timeout=60
```

**完成证据：** 纵向轨迹至少经历一次 Result 拒绝和一次进程边界恢复，仍在单次用户调用语义下继续；零错误 committed、零重复 Worker、零非预期用户交回。

## Milestone 4：让同一离线生产轨迹完整到 TERMINAL

**目的：** 在真实宿主花费 Token 前，先用生产资产走通整个生命周期，而不是再次只验证当前故障点。

**Files:**

- Modify: `tests/test_p0_e2e_product_closure.py`
- Modify: `tests/host_runtime/trajectory_runner.py`
- Modify: `tests/fixtures/golden/voice_clone/scenario.json`
- Modify: `scripts/product_acceptance.py`
- Modify: `tests/test_product_acceptance.py`

**实现：**

- 同一轨迹覆盖 setup → gap scan/review → architect → developer → critic → repair/refine → verification → terminal。
- 至少注入一次 Coordinator 结果修复、一次宿主会话中断恢复和一次 Critic P1 返工。
- 每次新失败先更新轨迹证据，再只修改其所属职责边界；不得为下一阶段预先扩展控制功能。
- 产品验收字段 `invocation_count`、`manual_protocol_repairs`、`unexpected_stops`、`traceability_complete` 和 `final_disposition` 必须从 EventStore/receipt 投影，不接受手填声明。
- Claude/Codex fake-host 使用同一生产 Skill、Command、Prompt、Action、Assembler 和 Tick 链，比较 Core 终态语义。

**EARS：** While 同一 Build 和设计场景分别由两个离线宿主执行, when 用户入口只调用一次, both trajectories shall 到达等价 `TERMINAL`，并证明追溯、返工、恢复和成本事实完整。

**验证：**

```bash
uv run pytest tests/test_p0_e2e_product_closure.py tests/test_product_acceptance.py -q --no-cov --timeout=120
```

**完成证据：** 双宿主离线生产轨迹均到 `TERMINAL`；零非预期停顿、零手工协议修复、零旧计划误续作；所有设计要求可追溯到任务和验收证据。

**成本证据：** 每条轨迹同时记录 Prompt/Envelope 字节数、Action context 数及 input/cache/output；静态执行包保持 KB 级而 token 偏高时，应减少 Action 内工具往返，不继续删减设计语义。

## Milestone 5：独立制品双宿主 L4 与发布结论

**目的：** 只用真实产品证据关闭 `P0-E2E`，不再让测试数量或 archive smoke 冒充完成。

> 2026-08-25 证伪修订：原 Milestone 4 测试读取 Canonical `context`，不能作为产品终态
> 证据。执行 Milestone 5 前必须先完成下列 M4-R 重建任务。

### M4-R：真实宿主边界重建

1. ✅ 建立 Host Execution Package 闭包：Coordinator/Worker Prompt 均有结构化引用，恢复包继承 `semantic_context_refs`。
2. ✅ Gap 输出改用人类可读 `section_ref`，由 Assembler 绑定内部 `section_id`。
3. ✅ 将 Assembler 拒绝纳入 `assembly_rejected → repair → prepared` 事务。
4. ✅ 纵向测试只消费 compact Action、Prompt Artifact、work files 和真实 operations。
5. ✅ 双宿主黑盒轨迹覆盖 Critic 返工并到 `TERMINAL`；Assembler/Core 拒绝与进程恢复
   由同一公开事务专项覆盖。

**EARS：** While installed product emits one Host Execution Package, when a host creates and
repairs Results, the complete run shall reach `TERMINAL` without reading Canonical private state,
guessing Core identity, repeating completed Workers, or returning an internal repair to the user.

## 规格覆盖

| 设计要求 | 对应里程碑 |
|---|---|
| 真实失败先进入生产轨迹 | 1 |
| 唯一设计工程模型 | 2、4 |
| Agent/机器事实分离 | 2 |
| Result 接受事务与自动恢复 | 3 |
| 单命令连续到 TERMINAL | 3、4 |
| 双宿主独立制品 L4 | 5 |
| L1-L3 不替代产品完成 | 5 |

计划没有独立的控制完美化任务；所有改动均由当前真实 L4 失败链或最终产品出口直接驱动。
