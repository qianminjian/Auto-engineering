# v5.8 真跑问题整改设计与 Spec（2026-08-05）

## 1. 目标与边界

本 Spec 将 `voice_clone_for_auto_CC_Design` 真跑报告中的问题转换为可执行的内核整改项。目标是：宿主交互可追溯、状态查询事实一致、外部项目目录可恢复、门禁结果不虚化，并让下一轮 Architect/Developer 继续完成业务代码缺口。

不把 Core 变成常驻 daemon，不在 Core 内调用 LLM，不直接替外部 Voice Clone 项目编写业务组件；业务缺口通过后续 Action/Batch 处理。

## 2. 逐问题根因与方案

| 编号 | 报告问题 | 根因判断 | 方案 | 取舍 |
|---|---|---|---|---|
| R1 | Gap Review 未逐项询问 | Action 只描述“对每个 gap”，状态没有单项游标，宿主可批量提交默认值 | 引入单 gap 交互协议：Action 明确 `interaction_mode=single_gap`、当前 gap、序号和剩余数；新宿主每次提交一个 decision，完成后 Core 再发下一个 Action | 多 Tick，但消除新宿主批量虚化；旧宿主批量 Result 保留兼容分支并不再由新 Action 生成 |
| R2 | `ae status` 返回空 | 统一 status 仍只读旧 checkpoints.db，未读取 EventStore projection | EventStore-first：优先读取 active thread 的 projection/action snapshot，旧 checkpoint 只作兼容 fallback；输出增加 `source`/`action` 可选字段，不破坏 7 字段 | 需要兼容旧项目；状态事实统一 |
| R3 | `dev-loop --status` 外部目录异常 | checkpoint 中只保存相对 `design_doc_path`，恢复时按进程 cwd 解析 | 初始化时将设计文档规范化为项目根下的绝对路径；恢复对历史相对路径按 project root 解析，并在路径失效时返回稳定错误而非 traceback | 绝对路径只写项目内路径，不泄漏宿主无关秘密 |
| R4 | Architect 组件映射/计划结构曾失败 | 标题展示文本与章节身份混用 | 保留已完成的规范化组件 ID 与 dry-run 结构门禁，纳入回归 Spec | 不再增加自由映射 |
| R5/R6 | 类型与 AudioSampleUpload 覆盖不足 | 业务代码批次计划未覆盖全部设计条目 | Core 在 PLAN_REFINE 中要求每个 finding 映射到 batch/task；下一轮由 Developer Action 实现并验证 | 不由治理内核越权改业务代码 |
| R7 | Gate 手工通过但运行记录失败 | timeout/not-found 用 `-1`，消息丢失；宿主命令与本地命令来源不一致 | 结构化 subprocess 状态（returncode、timed_out、not_found、stderr）；Gate 结果必须携带执行命令/来源，禁止用空消息解释失败 | 更长但可审计 |
| R8 | 多 Agent contract 不可用反复 hard-fail | 检测到 spawn proof 就强制要求 contracts，未区分“无跨 Agent 可验证契约” | 合同门禁分三态：有 executable contracts→执行；明确单 Agent/无跨模块边界→N/A；多 Agent 且声明了跨模块边界但缺契约→hard-fail | 不把不可适用误报为通过，也不让普通并行任务无限阻断 |
| R9 | P2 组件/Hook 细节缺口 | 业务批次尚未进入 refine 后的实现 | 作为本次真跑的 follow-up Spec，必须出现在 Architect refine 的 batch_plan 和 ProgressTree；Core 验证“finding→task”覆盖 | 由真实 Developer 产出代码与测试 |
| R10 | Loop 在 Tick 19 等待 | Tick 协议本身是离散、非 daemon；宿主未提交下一 Result | 保持非常驻设计，Action 增加 `continuation=required`、等待原因和下一步命令；宿主手册要求在非终态不得静默停留 | 避免引入后台进程/重复 LLM 成本 |

## 3. 可验收 Spec（EARS）

- While `gap_review` 有多个未决 gap, when Core 编译 Action, the Action shall 只暴露一个 `current_gap`、`gap_index`、`remaining_count`，并声明 `interaction_mode=single_gap`。
- While single-gap Action 由新宿主执行, when Result 明确声明 single-gap 却包含 0 个或超过 1 个 decision, the Core shall 返回稳定错误且不推进状态；未声明模式的历史 Result 仅走兼容分支。
- While EventStore 存在 active projection, when `ae status --format json` 执行, the CLI shall 返回真实 thread/stage/tick/action，且 `source=event_store`。
- While `design_doc_path` 是项目内相对路径, when 从任意 cwd 恢复, the Core shall 以 project root 解析并成功读取同一文档。
- While Gate 子进程超时或命令缺失, when Gate 记录结果, the result shall 保留 `timed_out/not_found/command`，不得仅显示 `exit=-1` 空消息。
- While contracts 为空且不存在声明的跨模块边界, when ContractGate 运行, the verdict shall 是 `not_applicable=true`，不得产生 `CONTRACT_CHECK_UNAVAILABLE` hard-fail。
- While Architect refine 返回 findings, when batch plan 校验, every finding shall 被至少一个 task 的 `finding_ref` 覆盖，否则计划无效。
- While Action 非终态, when 宿主完成当前阶段, the host shall 提交 Result 或明确报告 `continuation_required`，不得宣布完成或静默结束。

## 4. 实施顺序

1. 先落地本 Spec、实施计划和跟踪记录。
2. 实现设计文档路径恢复、EventStore-first status、Gate 结构化诊断。
3. 实现单 gap Action/Result 协议及 finding→task 门禁。
4. 更新宿主命令/Skill 文档，补充真实项目回归测试。
5. 串行运行专项测试、全量测试、静态检查；再由宿主重新执行 voice clone 真跑。
